# 크래프톤 인턴십 지원을 위한 포트폴리오 개편 방안

2026년 10월 19일 작성·보완. 지원 분야는 **2027 크래프톤 채용연계형 인턴십 Game Development – Programming**, 희망 직무는 **클라이언트 개발 1순위·엔진 개발 2순위**다. 이 문서는 개편 제안이며, 화면·고정 순서·글 변경을 적용했다는 기록은 아니다.

제출 대표 주소는 [DCB 포트폴리오](https://imjae.github.io/portfolio/dcb/)로 한다. **클라이언트 사례 3개 → 물·불의 런타임·그래픽스 사례 → 구체적인 AI 협업 사례**로 읽을 수 있게 만드는 것이 우선이다. Home 전체 재설계, 새 글 증설과 전 글의 형식 통일보다 기존 사례의 실제 장면·본인 판단·확인 범위를 보강한다.

문구는 [EDITORIAL.md](EDITORIAL.md), 작성·게시 절차는 [WRITING.md](WRITING.md), 촬영 기록은 [DCB-CAPTURE-PLAN.md](DCB-CAPTURE-PLAN.md)를 따른다. 기존 [글 작성 계획](DCB-WRITING-PLAN.md)의 날짜별 현황은 당시 기록이다. 이번 우선순위와 아래의 최신 확인 상태를 함께 사용한다.

공고가 실제 플레이 가능한 게임 개발을 설명하므로, 입력·상태·데이터·표현·도구·검증을 연결해 보여주는 방향을 권한다. 이는 포트폴리오 편집 판단이며 크래프톤의 공개된 채점표는 아니다.

## 3. 현재 상태와 증거의 범위

### 블로그

10월 19일 로컬 frontmatter에서 `draft: false`인 글은 77편, 그중 `project: dcb`는 **23편**이다. 초안은 1편이다. `cli-agent-harness`는 별도 `imjaess` 프로젝트이므로 DCB 글 수에 합치지 않는다. 기능 설정은 9개다.

Home은 고정 글 12편이며 게임 관련 9편 뒤에 AI 글 3편이 있다. 사용자가 정한 몬스터→FSM, 장비 조합→UI 이펙트, 짐 출렁임→흔들다리의 인접 순서를 유지한다. 현재 고정 목록을 개편 문서만으로 바꾸지 않는다.

다음은 **로컬 작성 상태**다. 공개 완료와 구분해야 한다.

- `src/pages/about.astro`의 소개 페이지와 메뉴·sitemap 연결.
- 물·FSM·워크트리 세 글의 기여 표 변경.
- 관련 인수인계·글쓰기 가이드 변경.

이 작업들은 이번 검토 시작 시 미커밋 상태였다. 게시 시에는 의도한 변경을 별도로 검토하고 같은 커밋의 Actions와 공개 주소까지 확인한다. 소개의 이름·위치·기간·팀 구성도 사용자 확인 없이 확정하지 않는다.

19일 복구 근거는 DCB의 「Sheet-Recovery-20261019」와 해당 manifest·실행 결과를 읽어 대조했다. 데이터 변경 `4e92ec04c`, 씬 변경 `25ff6a5bb`, 근거 보존 `bdf729f6a`에 연결된다. 입력은 Input System 가상 키보드였으며 일부 기존 에셋 경고도 남았다. 이번 문서 작업에서 Unity를 재실행한 것은 아니다.

엔진 2순위는 Unity 위에서 수행한 **데이터·메모리·스레드 경계·렌더링 API·측정 경험**으로 설명한다. 자체 게임 엔진 제작, 실시간 유체 전체 시뮬레이션, 검증하지 않은 C++ 숙련도나 서버 개발 경력을 추가하지 않는다. OpenGL·수학 글은 관련 개념을 설명하는 보조 링크로 두며 현재 컴파일·GPU 실행의 확인 범위를 유지한다.

밸런싱 목록은 삭제하지 않는다. [이동·재입력](../content/articles/gameplay/locomotion-stamina-reinput.md), [행동 비용·회복](../content/articles/gameplay/action-stamina-cost-and-recovery.md), [무게·갈증·물 보정](../content/articles/gameplay/movement-speed-modifier-stacking.md), [조정 도구](../content/articles/tools/player-balance-tuning-tool.md)를 통해 실제 호출·상태·데이터의 연결을 추가로 설명한다. 같은 표를 여러 글에 복사하기보다 현재 값을 설명하는 글로 연결한다.

## 5. 페이지별 최소 개편안

### 제출 진입점: DCB 포트폴리오

첫 화면에서 게임의 모습과 담당 범위, 대표 사례를 찾을 수 있게 한다. 영상 준비를 기다리며 전체 사이트를 다시 만들 필요는 없다.

1. 게임 한 줄 소개, 스택, 확인된 역할·기간·구성을 배치한다. 미확정 기간·팀원 수는 채우지 않는다.
2. 소개 문구 후보는 “조선을 배경으로 지게에 짐을 싣고 운반하는 액션 게임입니다. 이동·전투·장비 조합과 환경 상호작용을 개발하고 있습니다.”로 둔다. 지게 화물의 속도·소모·회복 곡선은 현재 배율 1이므로 적재량별 부담을 구현 성과로 앞세우지 않는다. 실제 적용되는 **인벤토리 무게·갈증·물속 보정**과는 구분한다.
3. 공개할 영상이 준비되면 기존 `content/project-videos/` 설정과 영상 링크 기능을 사용한다. 현재 기능은 외부 링크다. 상단 삽입 플레이어를 추가하는 작업과 혼동하지 않는다.
4. 핵심 3개, 물·불, 추가 기능을 구분해 읽을 수 있게 한다. 접기 UI보다 제목과 짧은 안내로 시작한다.
5. 핵심 사례 뒤에 “AI와 작업한 방식” 한 블록을 두고 워크트리 사례와 해당 게임 사례를 연결한다. AI는 작업 방식으로 설명하고 Unity·C#·HDRP 등의 기술 스택과 구분한다.

대상 파일은 `src/pages/portfolio/dcb.astro`, `src/data/dcb-features.mjs`다. 핵심 설명을 먼저 완성하고 기존 필드를 활용한다. 새 `summary` 객체나 공통 컴포넌트 도입은 반복을 줄일 필요가 확인될 때 진행한다.

### 기능 상세와 글

기존 **현재 기능 설명 한 편 → 구현·분석 글** 구조를 유지한다. 기능 설명의 첫 글을 기술 분석으로 교체하지 않는다. 상세 페이지는 게임에서 보이는 동작을 짧게 설명하고 문제 해결 과정으로 연결한다.

대표 글 도입부는 다음 네 가지를 짧게 답하게 한다. 아래는 작성 항목이며 확인되지 않은 성과를 채우는 양식이 아니다.

| 항목 | 넣을 내용 |
| --- | --- |
| 기능·문제 | 어떤 상황에서 무엇이 필요했거나 잘못됐는가 |
| 선택과 이유 | 어떤 방법을 선택했고 대안과 어떤 비용을 비교했는가 |
| 현재 결과·근거 | 구조 확인인지, 검사인지, 실제 실행인지 밝히고 대응 자료로 연결 |
| 역할·범위 | 본인이 정한 조건·수정 방향·판단, AI 수행, 재사용 자산과 남은 확인을 구분 |

기여 표는 대표 글에서 먼저 사용한다. “직접 정한 요구·판단 / 직접 수행이 확인되는 작업 / AI가 수행한 작업 / 재사용 자산”을 실제 기록에 맞춰 쓴다. AI가 검사 도구를 실행하고 사용자가 결과를 검토했다면 그 과정을 그대로 적는다. “검증은 모두 내가 직접 했다”로 단순화하지 않는다.

반복되는 일반 미검증 문장은 줄일 수 있다. 하지만 **과거 측정의 환경, 현재 꺼진 설정, 알려진 실패, 해당 기능의 미확인 왕복**은 관련 설명 옆에 남긴다. 끝의 검증 표에는 `날짜·대상 버전·실행 환경·방법·결과·남은 범위`를 모은다. 검사 코드의 존재와 검사를 실행한 사실도 구분한다.

물의 과거 CPU 중앙값 `54.7971 → 5.6990ms`를 사용한다면 초기 180프레임 캐시·배치 Editor·렌더링을 제외한 동기 평가라는 조건을 같은 위치에 표시한다. 현재 120프레임 보조 입자 캐시나 전체 게임 FPS·GPU 개선율의 수치로 바꾸지 않는다. FSM은 코드 기반 저작의 이점과 성능 개선 입증을 분리한다.

### Home과 소개

Home은 개발 블로그의 전체 진입점으로 유지하고 제출용 읽는 순서는 DCB 페이지에서 제공한다. 현재 Pinned 12편과 사용자가 지정한 인접 순서를 이번 문서 보완에서 바꾸지 않는다. 나중에 줄일 경우에도 AI 협업 대표 1편을 남기는 안을 우선 검토한다.

로컬 `/about/`에는 다루는 분야·기여·연락 경로와 먼저 읽을 글을 담는다. 학교·학점을 공개 소개에서 생략할 수 있다는 판단을 지원서 입력 생략으로 확대하지 않는다. 이름·위치·졸업 시점·기간·팀 구성은 확정한 사실만 사용한다. “공부한 내용을 정리합니다” 같은 작성 목적 안내는 기존 문구 지침과 대조해 수정한다.

“인턴쉽” 태그 일괄 변경과 GitHub 고정 저장소 재선정은 제출 후 항목으로 둔다. 표준 표기 “인턴십”으로 바꾸려면 기존 검색 URL도 확인한다. 저장소는 현재 코드·실행 상태·원본성과 공개 범위를 검토한 뒤 선택하며 이 계획에서 특정 저장소 고정을 완료로 취급하지 않는다.

## 6. AI 활용 능력을 보여주는 사례의 구성

AI 글을 많이 배치하는 대신 게임 작업 한 사례 안에서 판단 과정을 끝까지 보여준다. 기존 워크트리·FSM·물·IK 기록 중 **요청과 결과 근거가 연결되는 사례 하나**를 고른다. 아직 확인하지 않은 후보 비교를 새로 있었던 일처럼 만들지 않는다.

1. **문제와 성공 조건:** 무엇이 잘못됐고 어떤 코드·자산·동작을 보존해야 했는지.
2. **위임과 분해:** 어떤 조사·구현·검사를 AI에 맡기고 동시 작업 간 경계와 공유 입력을 어떻게 정했는지.
3. **후보와 판단:** AI 결과에서 무엇을 채택·수정·제외했고 무엇을 보고 결정했는지.
4. **검증:** 컴파일·자동 검사·화면·실제 플레이·측정 중 무엇을 누가 수행했고 무엇이 남았는지.
5. **통합과 다음 기준:** 변경을 어떤 순서로 합치고 이후 세션에 어떤 규칙을 남겼는지.

FSM 전환에서는 AI가 장기간 읽고 수정할 수 있는 패턴 원본을 만들려던 실제 동기를 유지한다. 그래프에서 코드로 바꾼 결과를 변경 범위 지정·차이 검토·검사 가능한 상태 정의와 연결한다. 당시 비용 우려를 전환 후 성능 개선 수치로 바꾸지 않는다.

[CLI 하네스](../content/articles/ai/cli-agent-harness.md)는 별도 `imjaess`의 경험 사례다. API 사용료 부담으로 CLI를 경유한 제작 배경, 역할 분리·결과 확인 구조, 느린 접근의 체감과 기존 도구로 충분해져 사용을 중단한 판단을 유지한다. 현재 주력 도구, API 대비 비용·성능 우위, 최신 제품의 객관적 비교 결과로 소개하지 않는다. 대표 AI 사례의 뒤에서 이어 읽는 회고로 배치한다.

이 구성은 공식 FAQ의 문제 정의·AI 협업 설명과 관련된다. 평가 문제를 예상하거나 통과를 보장하는 방식으로 쓰지는 않는다.

소개 영상은 기존 계획의 약 3분 편집안을 사용하고 더 짧은 구성이 가능하면 줄인다. 길이 맞추기보다 핵심 세 장면을 먼저 확보한다. 여러 글에 전체 영상만 반복하기보다 장면별 타임코드를 연결한다.

모든 첨부에는 촬영일, 대상 커밋·미커밋 변경 여부, Editor/Player, 해상도·녹화 fps·배속, 장면 범위를 기록한다. 녹화 fps는 게임 성능 수치가 아니다. 사용자가 공개할 구간을 정한 뒤 실제 URL을 붙이고 로그아웃 상태·모바일 재생을 확인한다. DCB에 자료가 존재한다는 이유만으로 공개 승인된 것으로 취급하지 않는다.
