2026년 10월 19일 작성. 이 블로그를 게임 프로그래머 지원용 포트폴리오로 재구성하는 계획이다. 2027 크래프톤 채용연계형 인턴십 Game Development – Programming(1지망 클라이언트, 2지망 엔진) 지원을 기준으로 삼았다. 서류 접수 마감은 2026년 10월 23일 11:59다. 문구 기준은 [EDITORIAL.md](EDITORIAL.md), 작성 절차는 [WRITING.md](WRITING.md), 촬영은 [DCB-CAPTURE-PLAN.md](DCB-CAPTURE-PLAN.md)를 따른다.

## 배경: 심사자 관점에서 본 현재 상태

공개된 DCB 글 24편, 포트폴리오·기능 페이지, Home, GitHub 프로필을 인사담당자 관점으로 검토했다. 심각도 순으로 정리한 미흡점은 다음과 같다.

| 순위 | 미흡점 | 근거 |
| --- | --- | --- |
| 1 | 저자가 구현자가 아니라 요청자로 읽힌다 | 기여 문장이 "코드·도구 작성에는 AI를 사용했다"로 수렴하고, 직접 설계·결정·디버깅한 항목을 분리한 글이 없다 |
| 2 | 실행 증거가 없다 | 24편 전부 이미지·영상 0건. 실측치는 과거 로그이며 본문에서 현재 결과로 쓰지 않는다고 밝힌다 |
| 3 | 면책 문장이 내용을 덮는다 | 글마다 미검증 표현 8~33회. 도입부에 "실행하지 않았다"가 굵게 들어간 글이 많다 |
| 4 | 코드가 없다 | DSL 글에 DSL, 셰이더 글에 셰이더, 도구 글에 도구 화면이 없다 |
| 5 | 엔진 2지망 근거가 약하다 | 저수준 내용은 물 캐시 재생과 밧줄 다리 글에만 있고 프로파일러·현재 수치가 없다 |
| 6 | 지원자 맥락이 없다 | 졸업 시점·역할·기간·팀 구성·"인턴쉽" 태그 의미가 어디에도 없다 |
| 7 | 결과가 앞에 없고 글이 길다 | 읽기 시간 10~18분, 핵심 수치가 뒤쪽 절에 있다 |
| 8 | 미완·꺼진 기능이 결론에 노출된다 | 포트폴리오 첫 문장의 적재 부담은 현재 데이터에서 중립이다 |
| 9 | 밸런싱 5편이 분량만 늘린다 | 같은 수치가 세 편 이상에서 반복된다 |
| 10 | Home 고정 12편 중 3편이 AI 협업 글이다 | 게임 프로그래밍 글보다 앞에 두면 포지셔닝이 흔들린다 |

강점도 있다. 포위 기준축의 데드밴드·슬루, 토큰·클레임 상한 예외, 발 인계 히스테리시스, 감쇠 스프링의 적분 시간 상한, 정점 레이아웃과 직접 버퍼 업로드처럼 문제를 이해한 사람만 쓸 수 있는 대목이 있다. 선택 이유와 trade-off가 적혀 있고, 설정값·측정값·검사 코드·검사 실행을 구분하는 태도는 신뢰 요인이다. 개편은 이 강점을 앞으로 꺼내고 증거를 붙이는 방향이다.

## 개편 원칙: 심사자의 읽기 경로

심사자는 세 단계로 읽는다. 각 단계에서 "무엇을 만들었나, 내가 한 것은 무엇인가, 증거는 무엇인가, 기술 깊이는 어느 정도인가"에 답해야 한다.

| 단계 | 시간 | 보는 화면 | 현재 상태 | 개편 후 |
| --- | --- | --- | --- | --- |
| 1차 | 30초 | Home, 포트폴리오 상단 | 영상 없음, 역할·기간 없음 | 소개 영상, 역할·기간·스택 한 화면 |
| 2차 | 3분 | 기능 카드, 대표 글 도입부 | 카드는 제목만, 글은 결과가 뒤에 있음 | 카드마다 결과·역할 한 줄, 글 상단 요약 블록 |
| 3차 | 15분 | 상세 글 | 깊이는 있으나 면책이 내용을 덮음 | 면책은 끝 한 절, 기여 표, 코드 발췌 |

개편은 1차와 2차 화면에 집중한다. 3차 글은 대표 3편만 손본다. 기존 글 주소·작성일·원본 보존 원칙은 유지한다.

## 페이지별 개편안

### Home

- 소개 문장 아래에 지원 분야와 역할 한 줄을 넣는다. 예: "게임 클라이언트·시스템 프로그래밍. Unity 6, C#, HDRP."
- Pinned 12편을 DCB 하이라이트 6편으로 줄인다. 순서는 IK 트레버설, Samurai 그룹 전투, 물 캐시 재생, 장비 파츠 조합, 밧줄 다리, Behavior→FSM 전환으로 둔다.
- AI 협업 3편은 Pinned에서 빼고 별도 작은 섹션으로 내린다.
- 소개 영상이 준비되면 Home에 썸네일 하나를 둔다.
- 관련 파일: `src/pages/index.astro`, `content/pins/`.

### 소개 페이지

- `/about/`에 이름, 위치, 연락, 다루는 분야, DCB 담당 범위, 먼저 읽을 글 3편, AI 사용 방식을 둔다. 2026년 10월 19일 로컬에 작성한 `src/pages/about.astro`를 기준으로 한다.
- 졸업 시점과 역할 한 줄을 추가한다. 공고는 학력을 요구하지 않고 졸업 시점만 조건이므로 학교·학점은 생략해도 된다.
- DCB 기간, 팀 구성, "인턴쉽" 태그의 의미는 사용자가 확정한 사실만 채운다. 비어 있으면 표시하지 않는다.

### 포트폴리오 상단

- 1~2분 소개 영상, 한 줄 요약, 기술 스택, 담당 범위, 기간과 팀 구성을 한 화면에 모은다.
- "지게 적재량에 따른 이동 부담"은 현재 카탈로그에서 적재 곡선이 배율 1이므로 문구를 바꾼다. 실제로 조정한 뒤에만 되살린다.
- 기술 스택 칩에서 "AI 협업"은 빼고 아래 담당 범위 문장에서 설명한다.
- 관련 파일: `src/pages/portfolio/dcb.astro`, `content/project-videos/`.

### 기능 카드

- 9개 카드를 핵심 5개와 나머지로 나눈다. 핵심은 IK 트레버설, Samurai 그룹 전투와 DSL, 물 캐시 스트리밍, 장비 조합 도구, 밧줄 다리 물리다. 나머지 4개는 접거나 아래로 내린다.
- 카드마다 "결과 한 줄"과 "내가 한 것 한 줄"을 추가한다. 결과 줄에는 수치나 영상 프레임이 있을 때만 수치를 쓴다.
- 밸런싱 5편은 카드 하나로 유지하되 Home·상단 노출에서는 제외한다.
- 관련 파일: `src/data/dcb-features.mjs`에 `outcome`, `role`, `evidence`, `primary` 필드를 추가하고 템플릿에서 렌더한다.

### 기능 상세 페이지

- 지금은 기능 설명 1편과 분석 글 목록만 있다. 상단에 케이스 스터디 요약 블록을 넣는다.
- 요약 블록 항목은 문제, 접근, 결과와 증거, 내 역할, 확인 범위, 기술 키워드다. 각 한 줄이다.
- 영상·캡처가 있으면 요약 블록 옆에 둔다.
- 관련 파일: `src/pages/portfolio/dcb/features/[feature].astro`, `src/data/dcb-features.mjs`.

### 글 템플릿

- DCB 구조 노트 상단에 같은 요약 블록을 붙여 결과를 먼저 보여 준다. frontmatter에 `summary` 객체를 추가하거나 본문 첫 절을 표로 쓴다.
- 면책은 본문 중간에서 걷어내고 끝의 "확인 범위" 한 절로 모은다. 도입부의 "실행하지 않았다" 굵은 문장은 요약 블록의 "확인 범위" 한 줄로 대체한다.
- 기여 절은 `구분 | 내용` 표로 통일한다. 행은 직접 정한 요구·조건·판단, 이 작업에서 설명할 수 있는 기여, AI를 사용한 것, 재사용 자산·외부 도구다. 2026년 10월 19일 물·FSM·워크트리 세 글에 먼저 적용했다.
- 대표 3편에는 본인 코드 발췌 10~30줄을 넣는다. DCB 소스는 비공개이므로 사용자가 허용한 범위만 쓰고 전체 파일·로컬 경로·개인 데이터는 넣지 않는다.
- 프로젝트 내부 용어는 첫 등장에서 한 줄로 풀어 쓴다. 대상: Wanderer, Deluge, Forest01Final, Wind·Press, 100·200 모션, MoveBlend.

### 증거

- 최소 단위는 촬영 계획의 CAP-01·02·04·05·07 다섯 장면과 약 1~2분 소개 영상이다. 글별 짧은 구간을 먼저 연결하고 소개 영상은 포트폴리오 상단에 둔다.
- 물 글에는 현재 120프레임 캐시의 Profiler 캡처 1장과 읽기·대기·업로드 수치 1세트를 넣는다. 조건은 캐시·카메라·시각·품질을 함께 적는다.
- 도구 글에는 에디터 화면 1장씩을 넣는다. 대상: Behavior DSL 뷰어, 플레이어 밸런싱 창, 장비 조립 프리뷰.
- 영상이 늦어지면 스크린샷을 먼저 넣고 캡션에 촬영 조건을 적는다. 빈 플레이어나 임시 썸네일은 넣지 않는다.
- 과거 측정값을 현재 결과로 바꿔 쓰지 않는다. 새 측정이 없으면 "당시 측정"으로 유지한다.

### AI 협업의 위치

- 카테고리는 유지하되 메인 축에서 내린다. Home Pinned와 포트폴리오 상단에서는 제외한다.
- 워크트리·하네스 글은 "개발 환경과 도구" 성격으로 설명하고, AI 사용은 각 글의 기여 표 안에서 다룬다.
- 크래프톤은 AI Native를 내세우고 AI 역량평가 전형이 있으므로 AI 사용을 숨기지 않는다. 목표는 "판단과 검증은 내가 했다"가 보이게 하는 것이다.
- 전환 동기가 "AI가 읽고 수정하기 쉽게"로 적힌 FSM 글은 게임 요구(패턴 추가 비용, Update 비용 우려)를 먼저 쓰고 AI 편집성을 그다음에 둔다.

### 태그와 GitHub

- "인턴쉽" 태그는 의미를 소개 페이지에 설명하거나 제거한다. 유지한다면 표준어 "인턴십"으로 바꾸고 기존 태그 주소의 이동을 확인한다.
- GitHub 고정 저장소를 LearnOpenGL, GameMath, UnityShader, P_FSM으로 바꾸고 소개에 블로그 포트폴리오 링크를 넣는다. 이 작업은 사용자가 GitHub에서 직접 한다.

### 엔진 2지망 보강

- 물 캐시 재생 글 한 편에 집중한다. 현재 수치·캡처·코드 발췌를 넣고, 정점 레이아웃·슬롯 선행 읽기·스레드 소유권·메모리 산정이 도입부 요약에 보이게 한다.
- OpenGL·게임 수학 글을 포트폴리오 하단에 "엔진·그래픽스 기초" 묶음으로 링크한다. 학습 기록이므로 구현 성과와 구분해 표기한다.
