# 블로그 문구 작성 지침

블로그의 제목, 요약, 본문, Home 소개, 메뉴와 검색·공유용 설명을 쓰거나 수정할 때 적용한다. 사용자가 추가로 정하는 문구 기준도 이 파일에 모은다. 파일 구성과 게시 절차는 [글쓰기 가이드](WRITING.md)를 따른다.

## 기본 방향

게임 개발과 학습 내용을 솔직하고 담백하게 쓴다. 무엇을 만들었고, 어떻게 구현했으며, 어디까지 확인했는지 독자가 알 수 있게 적는다. 포트폴리오 외에도 학습 메모, 오류 수정, 실험과 독서 기록을 같은 블로그에 남길 수 있다.

## 메뉴와 주제 표기

사용자 요청에 따라 블로그와 지원용 포트폴리오의 상단 메뉴, 주제 이름은 영어로 표시한다. 블로그의 주요 메뉴는 Writing, Portfolio, Projects, About 순서로 배치한다. Projects는 프로젝트의 대표 이미지와 이름을 앨범으로 보여 주고, 소개·기획서·리소스·개발 기록을 프로젝트별로 모은다. 소개와 기존 개발 글은 공개하며 기획서와 리소스 문서는 소유자만 열람한다. 왼쪽에는 별도의 Projects 영역을 두지 않는다. 홈 이동은 로고가 맡고 상단에는 별도의 Home 메뉴를 두지 않는다. GitHub는 오른쪽 보조 영역에 두며, 모드 전환은 View와 Edit를 사용한다. 주제는 Gameplay, Graphics, Tools & Systems, AI Collaboration, Notes, Mathematics, Books, Learning로 표기한다. 글의 제목·설명·본문과 작성 양식의 안내는 한국어를 유지한다.

Books에는 책 제목·저자와 독서 메모를 모은다. 완독일은 확인된 경우에만 입력하고, 글 작성일을 완독일로 대신하지 않는다. 짧은 감상은 사용자가 실제로 남긴 생각을 적으며 기존 요약을 개인 감상으로 바꾸어 쓰지 않는다.

제목이나 저자만 있는 노션 항목은 **감상 미작성** 목록으로 이관한다. 빈 글을 만들거나 읽은 경험·완독 사실을 추정하지 않는다. 같은 책의 여러 장과 별도 페이지의 감상은 책별로 합치고 중심 원문의 생성일을 쓴다. 다른 책의 감상이 함께 적혀 있으면 해당 책으로 모아 서로 연결한다. 기존 2024년 글을 보완할 때는 원래 날짜·slug와 보관 원문을 유지하며 노션 날짜를 별도로 남긴다.

## 해야 할 것

- **내용을 바로 말한다.** 제목에는 기능·문제·작업을, 요약에는 글에서 다루는 범위를 적는다.
- **공부용이라는 안내를 넣지 않는다.** 제목·요약·본문·사이트 소개에서 '공부를 위해 정리했다', '학습용 글이다' 같은 작성 목적을 직접 알리지 않는다. 기능·문제·개념을 바로 설명하고, 독립 예제·가상 데이터·원문 출처·AI 사용은 구체적인 사실로 유지한다.
- **구체적으로 설명한다.** 사용한 기술, 선택한 방식과 이유, 발생한 문제와 수정 내용을 쓴다. 기술 용어는 설명에 필요한 만큼 사용한다.
- **사실과 해석을 구분한다.** 구현한 기능, 소스에서 확인한 구조, 실제 실행 결과, 추정과 계획을 구분해서 표현한다.
- **성과에는 근거를 붙인다.** 개선을 설명할 때 비교 조건과 측정 범위를 함께 적는다. 아직 측정하지 않았다면 숫자를 만들지 않는다.
- **기능 설명에 필요한 사실을 쓴다.** 실제로 발생한 문제와 선택한 방법, 구현 결과를 설명한다. 성능 수치는 비교 조건과 함께 적고, 기술적 제약은 해당 동작 옆에서 설명한다.
- **기여 범위를 정확히 쓴다.** 직접 구현한 부분, AI를 사용한 부분과 재사용 자산을 구분한다. 글마다 필요한 범위에서 설명한다.
- **한 문장에 한 가지 내용을 담는다.** 긴 문장은 나누고, 같은 내용을 반복하는 문장은 줄인다. 소개는 짧게, 기술 설명은 이해에 필요한 만큼 쓴다.
- **존댓말로 문체를 맞춘다.** 블로그 글·요약과 포트폴리오는 `~했습니다 / ~합니다`체로 쓴다. `내가 정했다`는 `제가 정했습니다`처럼 고친다. 원문 인용과 코드 문법은 유지한다.

## 하지 말아야 할 것

- **과장이나 자기평가로 내용을 대신하지 않는다.** 근거 없는 ‘혁신적인’, ‘탁월한’, ‘완벽한’, ‘획기적인’ 등의 표현을 붙이지 않는다.
- **슬로건이나 비유를 억지로 만들지 않는다.** ‘개발 여정’, ‘가능성을 넓히는 도전’, ‘코드에 생명을 불어넣다’ 같은 표현을 소개나 제목의 기본 문구로 쓰지 않는다.
- **추상적인 말로 문장을 늘리지 않는다.** ‘핵심 가치를 실현했다’, ‘의미 있는 경험을 쌓았다’고 끝내기보다 실제 작업과 결과를 적는다.
- **독자에게 교훈을 선언하지 않는다.** ‘진정한 개발이란’, ‘단순한 구현을 넘어’ 같은 문구를 붙이거나, 모든 글을 거창한 깨달음으로 마무리하지 않는다.
- **생각과 감정을 지어내지 않는다.** 사용자가 말하지 않은 동기, 고민, 자신감, 감동이나 배움을 사용자의 경험처럼 쓰지 않는다.
- **확인 결과를 확대하지 않는다.** 일부 검사 통과를 전체 기능 완성으로, 특정 CPU 구간의 개선을 전체 FPS 개선으로 표현하지 않는다.
- **기여를 부풀리거나 생략하지 않는다.** 재사용한 모델·애니메이션·텍스처를 직접 제작했다고 쓰거나, AI 사용을 임의로 감추지 않는다.
- **모든 글을 지원용 자기소개로 바꾸지 않는다.** 학습·실험 기록에는 해당 내용에 필요한 설명을 쓴다. 문구 수정만으로 기술 내용이나 글의 의도를 임의로 삭제하지 않는다.
- **AI의 점검 메모를 공개 문구에 넣지 않는다.** 블로그 글과 포트폴리오에서 검사 실행·통과 건수 보고, `확인 근거` 같은 자료 대조 보고, `남은 확인` 칸, `이번 작성에서는 Unity를 실행하지 않았다` 같은 미실행 고지를 넣지 않는다. 이런 작업 기록은 내부 문서에 남긴다. 실제 문제 해결 과정·성능 수치·예제의 전제와 AI·재사용 자산의 기여는 유지하며, 고지를 삭제한 자리에 새 성과를 만들어 넣지 않는다.

## DCB 기능 설명과 분석

DCB 프로젝트의 기능별 목록은 **현재 기능 설명 한 편 → 구현·분석 글들** 순서로 구성한다. 첫 글은 플레이어가 무엇을 보고 어떻게 조작하는지, 현재 어떤 규칙·설정으로 동작하는지를 먼저 설명한다. 세부 코드, 문제 원인·수정 이력과 측정은 아래의 분석 글에서 다룬다. 기능 설명도 현재 소스·저장값과 실제 실행 확인을 구분하며, 지원 코드만 있는 기능을 현재 적용 상태로 소개하지 않는다.

지게 짐·다리의 물리 표현과 이동·행동 규칙은 기능 목록을 나눠 연결한다. 이동 속도·스태미너·회복·입력 제약과 기타 제어 요소는 **게임플레이 밸런싱과 제어**에서 다룬다. 밸런싱 글은 현재 규칙과 값의 적용 경로부터 설명하고, 조정한 경우 변경 이유·고정한 비교 조건·결과를 적는다. 작성 구조만 준비한 항목을 조정 완료나 플레이 성과로 소개하지 않는다.

## Learning의 C++ 객체와 메모리 글

1주차 글은 사용자가 C#·C 등에서 공통으로 쓰는 변수·조건문·반복문·함수 등의 기본 문법을 숙지했다고 전제한다. 다만 사용자 요청에 따라 포인터는 주소, 포인터 변수, 역참조와 멤버 접근, 널 포인터부터 다시 설명한다. 나머지 공통 문법의 입문 설명은 생략하고, C++의 값·참조, 소유권, 객체 수명, RAII와 복사·이동의 차이에 설명과 실습을 집중한다.

## CLI 하네스 글의 제작 배경

CLI 하네스 글의 사용 배경과 마무리는 사용자 요청에 따라 별도로 유지한다. API 사용료 부담으로 기존 계정의 CLI를 경유한 학습·경험용 프로젝트이며, 현재는 CLI 접근·응답의 체감 지연과 Codex·Claude Code의 기능 향상으로 별도 하네스가 필요하지 않아 사용하지 않는다는 개인 경험을 적는다. 이를 API 대비 성능 개선이나 최신 제품의 객관적 비교 결과로 확대하지 않는다. 이는 프로젝트의 제작 목적에 대한 설명이며, 블로그 글 자체를 공부용이라고 안내하는 기준과 구분한다.

## 작성 후 확인

- [ ] 제목과 요약만 읽어도 글에서 다루는 내용을 알 수 있는가?
- [ ] 과장, 비유, 슬로건이나 불필요한 자기평가를 줄였는가?
- [ ] 사용자가 말하지 않은 경험과 감정을 만들어 넣지 않았는가?
- [ ] 구현·검사·실행·측정 결과를 각각의 확인 범위에 맞게 썼는가?
- [ ] 직접 담당한 작업, AI 사용과 재사용 자산의 설명이 사실과 맞는가?
- [ ] 기술 내용과 원래 의도를 유지하면서 반복과 장식적인 문장을 줄였는가?

## 지침 추가와 수정

사용자가 문구에 관한 기준을 추가하거나 수정해 달라고 하면 해당 항목에 반영한다. 기존 항목과 겹치면 합치고, 충돌하면 최신 요청에 맞춰 고친다. 사용자가 확정하지 않은 선호를 사용자 지침으로 추가하지 않는다.

특정 문장이나 글에만 적용하는 요청은 적용 범위를 적는다. 사용자가 지침 변경을 요청한 경우를 제외하면 글을 작성하면서 이 지침을 임의로 완화하지 않는다.
