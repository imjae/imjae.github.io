# 블로그 문구 작성 지침

블로그의 제목, 요약, 본문, Home 소개, 메뉴와 검색·공유용 설명을 쓰거나 수정할 때 적용한다. 사용자가 추가로 정하는 문구 기준도 이 파일에 모은다. 파일 구성과 게시 절차는 [글쓰기 가이드](WRITING.md)를 따른다.

## 기본 방향

게임 개발과 학습 내용을 솔직하고 담백하게 쓴다. 무엇을 만들었고, 어떻게 구현했으며, 어디까지 확인했는지 독자가 알 수 있게 적는다. 포트폴리오 외에도 학습 메모, 오류 수정, 실험과 독서 기록을 같은 블로그에 남길 수 있다.

## 해야 할 것

- **내용을 바로 말한다.** 제목에는 기능·문제·작업을, 요약에는 글에서 다루는 범위를 적는다.
- **공부용이라는 안내를 넣지 않는다.** 제목·요약·본문·사이트 소개에서 '공부를 위해 정리했다', '학습용 글이다' 같은 작성 목적을 직접 알리지 않는다. 기능·문제·개념을 바로 설명하고, 독립 예제·가상 데이터·원문 출처·AI 사용과 실행 미검증 범위는 구체적인 사실로 유지한다.
- **구체적으로 설명한다.** 사용한 기술, 선택한 방식과 이유, 발생한 문제와 수정 내용을 쓴다. 기술 용어는 설명에 필요한 만큼 사용한다.
- **사실과 해석을 구분한다.** 구현한 기능, 소스에서 확인한 구조, 실제 실행 결과, 추정과 계획을 구분해서 표현한다.
- **성과에는 근거를 붙인다.** 개선을 설명할 때 비교 조건과 측정 범위를 함께 적는다. 아직 측정하지 않았다면 숫자를 만들지 않는다.
- **확인한 범위를 정확히 쓴다.** 컴파일, 자동 검사, 실제 플레이, 화면 비교와 성능 측정을 각각의 근거에 맞게 설명한다. 남은 문제는 관련 내용 옆에 짧게 적는다.
- **기여 범위를 정확히 쓴다.** 직접 구현한 부분, AI를 사용한 부분과 재사용 자산을 구분한다. 글마다 필요한 범위에서 설명한다.
- **한 문장에 한 가지 내용을 담는다.** 긴 문장은 나누고, 같은 내용을 반복하는 문장은 줄인다. 소개는 짧게, 기술 설명은 이해에 필요한 만큼 쓴다.
- **글 안의 문체를 맞춘다.** 소개와 안내는 간단한 `~합니다`체, 기술 글과 메모는 `~했다 / ~한다`체를 기본으로 한다. 사용자가 지정한 문체가 있으면 따른다.

## 하지 말아야 할 것

- **과장이나 자기평가로 내용을 대신하지 않는다.** 근거 없는 ‘혁신적인’, ‘탁월한’, ‘완벽한’, ‘획기적인’ 등의 표현을 붙이지 않는다.
- **슬로건이나 비유를 억지로 만들지 않는다.** ‘개발 여정’, ‘가능성을 넓히는 도전’, ‘코드에 생명을 불어넣다’ 같은 표현을 소개나 제목의 기본 문구로 쓰지 않는다.
- **추상적인 말로 문장을 늘리지 않는다.** ‘핵심 가치를 실현했다’, ‘의미 있는 경험을 쌓았다’고 끝내기보다 실제 작업과 결과를 적는다.
- **독자에게 교훈을 선언하지 않는다.** ‘진정한 개발이란’, ‘단순한 구현을 넘어’ 같은 문구를 붙이거나, 모든 글을 거창한 깨달음으로 마무리하지 않는다.
- **생각과 감정을 지어내지 않는다.** 사용자가 말하지 않은 동기, 고민, 자신감, 감동이나 배움을 사용자의 경험처럼 쓰지 않는다.
- **확인 결과를 확대하지 않는다.** 일부 검사 통과를 전체 기능 완성으로, 특정 CPU 구간의 개선을 전체 FPS 개선으로 표현하지 않는다.
- **기여를 부풀리거나 생략하지 않는다.** 재사용한 모델·애니메이션·텍스처를 직접 제작했다고 쓰거나, AI 사용을 임의로 감추지 않는다.
- **모든 글을 지원용 자기소개로 바꾸지 않는다.** 학습·실험 기록에는 해당 내용에 필요한 설명을 쓴다. 문구 수정만으로 기술 내용이나 글의 의도를 임의로 삭제하지 않는다.

## DCB 기능 설명과 분석

DCB 프로젝트의 기능별 목록은 **현재 기능 설명 한 편 → 구현·분석 글들** 순서로 구성한다. 첫 글은 플레이어가 무엇을 보고 어떻게 조작하는지, 현재 어떤 규칙·설정으로 동작하는지를 먼저 설명한다. 세부 코드, 문제 원인·수정 이력과 측정은 아래의 분석 글에서 다룬다. 기능 설명도 현재 소스·저장값과 실제 실행 확인을 구분하며, 지원 코드만 있는 기능을 현재 적용 상태로 소개하지 않는다.

## 작성 후 확인

- [ ] 제목과 요약만 읽어도 글에서 다루는 내용을 알 수 있는가?
- [ ] 과장, 비유, 슬로건이나 불필요한 자기평가를 줄였는가?
- [ ] 사용자가 말하지 않은 경험과 감정을 만들어 넣지 않았는가?
- [ ] 구현·검사·실행·측정 결과를 각각의 확인 범위에 맞게 썼는가?
- [ ] 직접 담당한 작업, AI 사용과 재사용 자산의 설명이 사실과 맞는가?
- [ ] 기술 내용과 원래 의도를 유지하면서 반복과 장식적인 문장을 줄였는가?

## 지침 추가와 수정

사용자가 문구에 관한 기준을 추가하거나 수정해 달라고 하면 해당 항목에 반영한다. 기존 항목과 겹치면 합치고, 충돌하면 최신 요청에 맞춰 고친다. 사용자가 확정하지 않은 선호를 사용자 지침으로 추가하지 않는다.

특정 문장이나 글에만 적용하는 요청은 적용 범위를 적는다. 사용자가 지침 변경을 요청한 경우를 제외하면 글을 작성하면서 이 지침을 임의로 완화하지 않는다.
