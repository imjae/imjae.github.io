# DCB 포트폴리오 글 작성 계획

2026년 10월 19일 시작할 촬영의 장면별 지시·첨부 위치·YouTube 삽입·기록 양식은 [촬영·첨부 준비](DCB-CAPTURE-PLAN.md)를 따른다. 아래 일정과 공개 글 수는 최초 계획 당시의 기록이다.

2026년 10월 17일 기준 작성 계획이다. DCB의 「크래프톤 인턴 지원 계획」과 공개 글을 대조했다. 대표 사례 다섯 개의 구조 설명은 공개되어 있으며, 다음 작업은 실제 동작과 본인 판단을 보여주는 근거를 보강하는 것이다. 신규 글은 최대 두 개의 후보로 좁히고, 기존 글 보완과 지원 제출물을 먼저 마친다.

## 지원 방향과 블로그의 역할

- 지원 분야는 Game Development – Programming, 희망 직무는 클라이언트 개발 1순위·엔진 개발 2순위다.
- 대표 사례는 IK 트레버설, 몬스터 패턴·그룹 전투, 2D·3D 장비 파츠 조합, 물 캐시 재생, 불·VFX 저작의 다섯 가지다. 지게 운반으로 프로젝트의 기본 플레이를 설명한다.
- 기여 범위는 3D 모델·애니메이션 원본 제작을 제외한 기획과 구현·검증이다. 글마다 AI 사용과 재사용 자산을 함께 설명한다.
- 블로그의 기존 개요 글을 사례별 기술 설명과 증거로 보완한다. PDF·영상·자기소개서는 기존 지원 계획의 별도 제출물이며, 이번 작업에서 완성한 것으로 취급하지 않는다.
- 새 글은 `draft: true`로 작성한다. 공개 글 변경과 초안 게시도 사용자의 요청 범위에 맞춰 진행한다.

공식 모집 안내에서 **2026년 10월 23일 오전 11시 59분(KST) 마감**을 다시 확인했다. 기존 목표는 **22일 저녁 제출**이다. [크래프톤 공식 모집 안내](https://www.krafton.com/careers/pioneer/)

지원서 문항·첨부 용량·저장 규칙은 실제 제출 준비 때 양식에서 다시 확인한다.

## 현재 공개 상태와 우선순위

공개 글은 11개다. 개발 관련 글 9개와 2024년 글 2개로 구성되며, 물 깊이 글 1개는 초안이다. 지게 운반, 워크트리 병행 작업과 CLI 하네스 글은 공개를 마쳤다. 이 문서는 블로그 본문과 별도로 관리하는 로컬 지원 준비 문서다.

AI 글은 일반적인 구현·검증 과정, 워크트리 운영, CLI 하네스 제작까지 세 가지가 있다. 클라이언트 개발 1순위라는 지원 방향에 맞춰, 다음 순서는 **몬스터·장비·IK의 구체적인 문제와 동작 근거 → 물·불의 실행 근거 → AI 후보 채택 사례**로 잡는다. 이 순서는 작성 우선순위이며 공식 평가 배점은 아니다.

촬영의 선행 조건은 게임 진입이다. 10월 16일 감사에서는 시트 누락으로 일반 시작이 중단됐다. 17일 복구 완료를 확인할 새 실행 기록은 이번 검토에 없으므로, 촬영 계획은 DCB에서 일반 시작·재시작 상태를 먼저 확인한 뒤 확정한다. 블로그 작업에서 DCB를 수정하거나 Unity 검사를 실행하지 않는다.

## 기존 일정에서 가져온 작업 순서

기존 계획은 10월 17일부터 22일까지 하루 8시간, 총 48시간이다. 아래 표는 당시의 목표이며 완료 표시가 아니다. 게임 복구·촬영 작업은 DCB에서, 글 작성과 사이트 검증은 이 블로그 프로젝트에서 진행한다.

| 날짜 | 기존 지원 준비 목표 | 블로그에서 사용할 결과 |
| --- | --- | --- |
| 10월 17일 | 시트 데이터와 일반 시작·재시작 복구 | 촬영 가능한 기능과 실행 제한 확인 |
| 10월 18일 | 다섯 사례와 지게 기능 검증, 물 검사 2건 정비 | 재현 조건, 검사 결과, 남은 문제 확정 |
| 10월 19일 | 사례별 촬영과 약 3분 영상 편집, 새 기능 추가 중단 | 사용자 승인 캡처·영상과 비교 조건 확보 |
| 10월 20일 | 12쪽 이내 포트폴리오 PDF와 이력서 초안 | 블로그 설명과 제출물의 기여·결과 표현 대조 |

23일 오전은 제출 장애 대응 시간으로 남긴다. 실행 복구가 늦어지면 추가 측정과 영상 분량을 줄이고, 확보한 근거만으로 설명한다. 새 로비·마을 재건은 이번 제출의 구현 성과에 넣지 않는다.

## 기존 글에 추가할 내용

기존 공개 글의 주소와 시리즈 순서는 유지한다. 같은 구조를 다시 설명하는 글을 늘리기보다 기존 글에 문제·판단·증거를 보강한다.

| 순서 | 대상 | 이어서 작성할 내용 | 필요한 증거 |
| --- | --- | --- | --- |
| 1 | [몬스터 전투](../content/articles/gameplay/monster-combat.md) | 플레이어의 방향 전환에 몬스터 전체가 따라 도는 문제를 예로 들어 기준축·각도 여유·추종 속도를 선택한 이유를 설명한다. 개별 DSL의 상태 전이와 그룹의 공격 허가도 한 장면에서 연결한다 | 같은 조건의 방향 전환 비교, 다수 공격 기회 배분, 공격 중단·사망·해제 후 점유 반환. 관련 검사와 실제 반복 전투는 따로 기록 |
| 2 | [장비 파츠 조합](../content/articles/tools/modular-equipment.md) | 파츠 트리의 구체적인 예 하나를 2D·3D·저장까지 따라간다. 공통 조립 순서와 표현별 피벗·스케일 처리, 복사본·풀 반환 경계를 설명한다 | 같은 파츠의 2D 조립→3D 프리뷰·장착→드랍·회수→저장·재실행. 복원 전후 트리·스탯, 원본 보존과 이전 파츠 잔존 여부 |
| 3 | [IK 트레버설](../content/articles/gameplay/ik-traversal.md) | 접촉이 끊기는 구간 하나를 정해 진입·지지·해제·보행 인계를 풀어 쓴다. 루트 이동과 캐릭터 제어, 관절 굽힘 보정의 역할을 구분한다 | 같은 Avatar·지형·입력의 정상 속도·손발 근접 비교. 후보 하나의 채택·제외 이유와 높은 StepUp의 잔여 결함을 함께 표시 |
| 4 | [물 캐시 재생](../content/articles/graphics/water-playback.md) | 세 프레임 슬롯의 재사용, 선행 읽기 지연 시 처리, 메인 스레드 업로드와 메모리의 절충을 구체화한다 | 현재 캐시·카메라·해상도·품질을 명시한 재생과 seek·loop·정지·재개. 성능을 주장할 때는 측정 구간·표본 수와 CPU 읽기·업로드·GPU 시간을 구분. 실패 검사 두 건의 정비 여부 갱신 |
| 5 | [불과 VFX](../content/articles/graphics/fire-vfx.md) | 화염 품질 단계와 애니메이션 이펙트 저작을 소제목으로 구분한다. 단계 경계의 hysteresis, 시간 유지, 첫 재생 준비와 부착점 선택 이유를 설명한다 | 같은 불의 근거리·원거리·경계 이동·정지·재개, 타임라인 편집 화면과 게임에서의 발생 프레임·부착점. 빌드 재생은 확인한 경우만 결과 추가 |
| 6 | [지게 운반](../content/articles/gameplay/jige-carry-burden.md) | 현재 구조 설명에 짧은 운반 시연을 붙인다. 착용 규칙과 적재 곡선의 실제 적용 상태를 캡션에도 명시한다 | 같은 길의 맨몸·빈 지게·적재 비교, 내려놓기 후 보정 해제, 고갈 후 버튼 유지·재입력과 행동 종료 후 회복. 적재 곡선이 모두 1인 현재 설정에서는 적재량 차이의 효과를 주장하지 않음 |
| 7 | [AI 협업](../content/articles/ai/working-with-ai.md) | 실제 문제 하나의 요구사항→AI 제안→본인 판단·수정→검증을 추가한다. 워크트리·하네스 글과 구체적인 후보 비교 사례로 연결한다 | 후보 차이와 채택·기각 이유, 같은 조건의 비교 자료. 도구가 수행한 일과 본인이 지시·판단한 일을 기록에 맞춰 구분 |
| 8 | [워크트리 병행 작업](../content/articles/ai/parallel-ai-worktrees.md) | 겹치는 세션·선점·공유 입력·체리픽·실험 정리 설명은 이미 있다. 통합 사례 하나에 작업별 변경 범위와 반영 순서를 간략히 보충한다 | 공개 가능한 변경 목록이나 직접 그린 통합 도식. 원본 로그·개인 경로를 붙이지 않고, 성과 수치는 새 측정이 있을 때만 추가 |
| 9 | [CLI 하네스](../content/articles/ai/cli-agent-harness.md) | API→CLI 전환과 입출력·판정 경로는 이미 있다. 작업 등록·역할 실행·판정 사례에 실패 시 `needs_fix`와 재시도, 통과 후 검토 대기를 연결한다 | 인증 정보와 경로를 제거한 관리 화면. 실제 CLI provider·mock 해제 상태의 작은 작업과 실패 처리 결과를 확인한 뒤 추가. 이번 검토에서는 실계정 호출하지 않음 |

몬스터·장비·IK는 소스 구조와 기존 기록으로 기술 설명을 먼저 보강할 수 있다. 실제 재생 성공·복원 일치·성능 개선의 결과는 각각의 확인 자료가 생긴 뒤 추가한다. 각 대표 글에는 문제 하나, 선택 이유, 실제 화면, 확인 조건과 남은 문제를 갖추는 것을 목표로 한다.

지게 글은 프로젝트의 기본 플레이를 설명하는 보조 글로 사용한다. 물 깊이 초안은 이번 대표 사례와 별도로 유지한다.

## 추가 글 후보

제출 전 신규 글은 아래 두 개를 후보로 둔다. 대표 글과 PDF·영상 준비가 늦어지면 해당 내용은 기존 글의 한 절로 넣는다.

| 우선순위 | 가제와 분류 | 다룰 내용 | 작성과 공개 조건 |
| --- | --- | --- | --- |
| 1 | AI가 제안한 IK 보정 후보를 비교한 과정 · `ai` | 같은 지형에서 후보 두세 개를 비교해 접촉 수치·관절 외형·보행 연결 중 무엇을 기준으로 채택·제외했는지 설명한다. 기존 워크트리 글의 운영 과정과 연결한다 | 실험 기록과 비교 가능한 승인 이미지 확보. 검사 통과와 시각적 완성도를 구분하며, 높은 StepUp 문제를 해결했다고 확대하지 않음 |
| 2 | 시트 데이터 누락으로 멈춘 게임 시작을 진단하고 복구한 과정 · `tools` | 일반 시작과 다운로드 경로, 누락된 스냅샷, 유효 데이터 검사, 재시작과 빌드 재현 과정을 설명한다 | 진단은 10월 16일 기록이 있으나 복구 완료는 미확인. DCB에서 복구·일반 시작·재시작 결과를 확보한 뒤 결과까지 작성. 원본 시트 주소와 개인 저장 데이터는 공개하지 않음 |

추가 여유가 생기면 **실제 물 캐시에 종속된 검사를 합성 데이터로 분리한 과정**, **애니메이션 VFX 타임라인 저작 도구**를 후속 주제로 검토한다. 전자는 검사 정비가 끝났을 때, 후자는 편집·프리뷰·게임·빌드의 연결을 독립적으로 설명할 자료가 있을 때 다룬다. 현재는 물·불 글의 보완을 우선한다.

## 포트폴리오 페이지와 제출물 연결

- [DCB 포트폴리오 페이지](../src/pages/portfolio/dcb.astro)의 첫 화면에 실제 게임 장면과 짧은 시연 링크를 배치한다. 현재의 시스템 개념도와 실제 화면을 구분한다.
- 대표 사례는 클라이언트 세 개를 앞에, 물·불 두 개를 뒤에 둔다. 지게 운반 글은 게임 소개 옆에서 연결한다. 현재 적재 곡선과 소개 문구가 같은 상태를 설명하는지 확인한다.
- 각 사례는 문제와 선택 이유를 짧게 소개한 뒤 상세 글로 연결한다. 실행·관측 결과와 소스 설명의 날짜를 대조한다.
- AI 자료는 구체적인 후보 판단 사례, 워크트리 운영, CLI 하네스 순으로 찾아갈 수 있게 연결한다. 하네스의 프로젝트는 `imjaess`로 유지한다.
- PDF·영상과 블로그에서 사용한 수치·환경·본인 기여·AI 보조·재사용 자산의 표현을 맞춘다. 그래픽스 사례는 Unity 런타임의 데이터·메모리·렌더링 경험으로 설명한다.

## 가져온 검증 기록의 범위

10월 16일 기록은 지게 선택 검사 10/10, 트레버설 116/116, 불 22/22, 물 17/19 통과다. 몬스터와 장비 검사는 이 실행에 포함되지 않았다. 이번 글 작성 중 Unity 검사나 실제 플레이를 다시 실행하지 않았다.

당시 Windows 빌드 생성은 성공했으나 일반 시작은 데이터 누락으로 게임 진입에 실패했다. 빌드 생성, 그래픽 없는 기동, 실제 화면·조작을 구분한다. 당시 결과를 현재 플레이 가능 상태로 확대하지 않는다.

물의 두 실패, 높은 StepUp의 접촉·발 튐, 장비 조립 왕복과 반복 전투의 미확인 범위를 각 글에서 유지한다. 현재 설정의 변경이나 추가 검증이 확인되면 날짜와 조건을 함께 갱신한다.

## 첫 초안에서 확인한 설정 차이

10월 17일 지게 문서와 현재 소스·카탈로그를 대조했다. 계산 코드는 적재율 곡선을 지원하지만, 저장된 `GameBalanceCatalog`의 적재 속도·소모·회복 곡선은 모두 배율 1이다. 착용 상태별 규칙은 별도로 설정되어 있다. 코드 기본 곡선이나 과거 문서의 예상 속도를 현재 적용 결과로 쓰지 않는다.

대조한 식별자는 `JigeCargo`, `Player.CarryBurden`, `WandererCarryBurdenBalance`, `Player.Input`, `Player.Attribute`, `GameBalanceCatalog`, `JigeCarryBurdenBalanceTests`다. 비공개 소스 전체, 원본 로그, 개인 데이터는 옮기지 않았다.

## 글을 마칠 때 확인할 항목

- 구현 구조, 현재 설정, 과거 검사, 이번 실행 결과를 구분했는지 확인한다.
- 그림은 설명용 구조도로 표시하고 실제 게임 화면처럼 사용하지 않는다. 캡처·영상은 승인된 자료만 사용한다.
- 남은 캡처·측정은 관련 설명 옆에 적는다. 자료가 없는 결과나 수치를 채워 넣지 않는다.
- `npm run verify` 후 Home, 긴 본문과 모바일 검색을 확인한다. 초안이 공개 빌드·검색·RSS·sitemap·수정 목록에 포함되지 않는지 확인한다.
- 게시 요청이 있으면 의도한 파일만 커밋·push하고 Actions와 실제 공개 페이지를 확인한다.
