# 글쓰기와 정리 가이드

글은 Markdown 파일 하나로 작성합니다. 폴더는 넓은 기술 영역, 태그는 세부 기술, 시리즈는 읽는 순서, 프로젝트는 소속 작업을 뜻합니다.

주제는 Gameplay(`gameplay`), Graphics(`graphics`), Tools & Systems(`tools`), AI Collaboration(`ai`), Notes(`notes`), Mathematics(`math`), Books(`reading`), Learning(`study`)를 사용합니다. 수학의 수·함수·벡터·행렬·회전 설명은 `math`에 모으고, 엔진이나 렌더링 API를 중심으로 다루는 글은 해당 기술 주제에 둡니다. 책 목록과 독후감은 `reading`에 모읍니다. 개념을 순서대로 다루는 계획과 그에 따른 실험 기록은 `study`에 모읍니다.

문구를 작성하거나 수정하기 전에 [블로그 문구 작성 지침](EDITORIAL.md)을 읽습니다. 이 문서는 파일 구성과 게시 절차를 다룹니다.

Learning는 과정별 입구를 먼저 표시합니다. `src/data/study-courses.mjs`에서 과정 제목·계획 글·주차별 제목을 관리하며, `/series/<과정 id>/`에서 전체 계획과 주차별 목록을 보여 줍니다. 글에 같은 `series`를 지정하고, 전체 계획은 `order: 1`, 주차별 글은 주차에 1을 더한 `order`를 사용합니다. 주차 데이터의 `articleSlug`에는 실제 작성한 글만 연결합니다. 공개되지 않은 주차는 공개 화면에서 링크 없는 **작성 예정**으로 표시하고, 로컬 dev에서는 초안도 열 수 있습니다. 본문 검색은 Writing에서 제공합니다.

DCB의 기능별 이식 과제는 `dcb-unreal-port`, C++과 엔진 내부 구조는 `unreal-cpp-engine` 과정에 둡니다. 이식 과정은 게임에서 바꿀 동작·적용할 엔진 기능·실행 순서·완료 기준을 연결하고 필요한 기존 글을 참조합니다. 공개 글 수는 구현 완료 수가 아닙니다. 실제 결과를 추가할 때는 실행 조건과 직접 수행한 변경을 기록합니다. 과정의 `label`은 Learning 카드의 영문 기술 표기이며, 생략하면 기존 C++ 표기를 사용합니다.

## 나만 보는 글과 공개 범위

로그인 후 화면 하단의 **전체 관리 → 내 글 · 공개 / 비공개**에서 작성합니다. 제목·요약·주소·작성일·주제·본문을 입력하고 **글 저장**을 누르면 비공개로 저장됩니다. 비공개 글은 소유자 계정으로 로그인한 경우에만 목록과 본문을 볼 수 있습니다. 이 글의 원문은 Cloudflare의 소유자 글 저장소에 보관하며 공개 GitHub 파일이나 정적 검색 색인에 넣지 않습니다.

저장한 글의 **공개** 토글을 켜고 확인하면 로그인 없이 읽을 수 있고 Writing과 일반 주제 검색에 표시됩니다. 토글을 끄면 서버가 즉시 비공개로 전환합니다. 변경한 본문은 먼저 저장한 뒤 공개 범위를 바꿉니다. 공개 중인 글의 본문 저장은 공개 내용에 바로 반영됩니다. 이미 다른 사람이 읽거나 보관한 사본까지 회수하는 기능은 아닙니다.

기존 GitHub 글은 **공개 글 관리 → 공개 / 비공개**에서 옮깁니다. 원문을 비공개 저장소에 먼저 보관한 뒤, 안내된 GitHub 화면 두 곳에서 **이전 설정 저장**과 **공개 원본 제거**를 각각 Commit changes로 확정합니다. 공개·편집 배포와 기존 주소의 연결, 현재 GitHub 원본 제거를 확인하기 전에는 **이전 대기**로 표시합니다. 이후 기존 `/writing/<slug>/` 주소는 서버 글로 연결되고 같은 토글을 사용합니다. 과거 GitHub 커밋 이력은 남습니다. 기존 2024년 글의 `legacy/jekyll/` 원본은 제거하지 않습니다.

Markdown 파일은 **Markdown 파일 가져오기 → 글 저장**으로 비공개 보관할 수 있습니다. 기존 GitHub 초안도 원래 공개 저장소의 파일과 이력은 남으므로, 민감한 새 내용은 이 화면에서 작성합니다. **저장본 내려받기**는 개인 백업용이며 공개 저장소에 추가하지 않습니다. 비공개 원문은 브라우저 localStorage나 sessionStorage에 보관하지 않습니다.

서버 글은 Writing의 실시간 목록·검색과 직접 주소에서 읽습니다. GitHub 파일 기반의 Home 고정·Learning 과정·시리즈·기존 RSS·사이트맵에는 포함하지 않습니다. 공개 범위를 바꾼 뒤에도 정적 파일에 제목·본문이 남지 않도록 두 저장 방식을 구분합니다. Markdown의 표·코드·수식·Mermaid·이미지와 허용한 YouTube 임베드를 표시하며, 스크립트와 임의 iframe은 제거합니다.

## Projects와 프로젝트 문서

`/projects/`는 프로젝트의 표지와 이름을 앨범으로 보여 줍니다. 공개 목록·소개는 `src/data/projects.mjs`, 표지는 기존 `public/media/games/`에서 관리합니다. 현재 DCB, 도형 공방, 던전 탐사를 등록했습니다. 표지 출처와 생성 프롬프트는 [프로젝트 표지](GAMES-MEDIA.md)에 기록합니다.

프로젝트를 선택하면 `/projects/<id>/`에서 공개 소개를 먼저 보여 줍니다. DCB는 기존 소개·영상·기능 목록과 개발 기록을 유지합니다. 상단의 **기획서**·**리소스** 탭은 각각 `/projects/<id>/plans/`·`/projects/<id>/resources/`로 연결됩니다. 공개 사이트에서는 비공개 안내만 표시하고, **소유자 로그인** 후 같은 경로의 보호된 화면에서 읽고 편집합니다.

프로젝트 이름 아래에 소개·기획서·리소스·개발 기록 탭을 둡니다. 소개는 대표 이미지와 본문을 한 글로 읽고, 개발 기록은 제목·주제·날짜·요약 목록으로 표시합니다. DCB 개발 기록의 기존 `/series/dcb/` 주소는 유지합니다. 다른 프로젝트의 글에는 `project: shape-workshop` 또는 `project: dungeon-exploration`을 지정하면 해당 프로젝트의 개발 기록에 표시됩니다.

기획서는 **기획서 추가**에서 제목·폴더·본문을 작성합니다. 폴더에 `게임플레이/전투`처럼 `/`로 하위 경로를 적으면 트리로 묶입니다. 8단계까지 사용할 수 있고 비워 두면 최상위에 표시합니다. 트리 옆에서 선택한 본문을 읽고 제목·폴더로 검색할 수 있습니다. 모바일에서는 목록을 접고 펼칩니다. 리소스는 **리소스 추가**에서 제목·대표 이미지 주소·이미지 설명·본문을 입력합니다. 선택한 큰 이미지와 썸네일 목록을 함께 보며 목록은 12개씩 표시합니다. HTTPS 이미지 파일 주소나 공개 사이트의 `/media/`, `/assets/` 경로를 연결하며 파일 업로드 기능은 포함하지 않습니다.

문서의 **Edit**는 현재 선택한 문서를 수정합니다. **저장**은 서버에 반영하며 같은 문서의 Edit로 돌아옵니다. **View** 또는 **본문 보기**로 읽습니다. 저장되지 않은 수정은 화면을 떠날 때 확인하고, 다른 탭에서 먼저 저장했다면 덮어쓰지 않고 충돌을 알립니다. 기획서와 리소스의 목록·본문에 예시 데이터를 자동으로 넣지 않습니다.

기획서와 리소스는 기존 GitHub 소유자 한 명만 읽고 수정합니다. 기존 Durable Object 인스턴스 `game-plans`와 기획서 키 `game-plan:<id>`를 그대로 사용하며, 리소스 키는 `project-resource:<id>`로 분리합니다. 공개 범위 전환 기능은 없습니다. 본문은 GitHub 저장소·정적 빌드·검색·RSS·사이트맵·브라우저 저장소에 넣지 않습니다. 공개 데이터 파일에 비공개 본문을 추가하지 마세요. 자료를 자동으로 가져오지 않으며 아직 저장한 내용이 없으면 로그인한 화면에 빈 상태를 표시합니다.

기존 `/games/`는 `/projects/`로, `/games/<id>/`는 해당 프로젝트의 기획서로 연결하며 `edit` 쿼리도 유지합니다. 기존 `/api/game-plans/<id>`와 `/api/project-documents/<id>/<plans|resources>`는 이전 본문을 다루는 호환 API로 유지합니다. 기존 본문은 `main` 문서로 읽으며 저장 키·내용·버전을 그대로 사용합니다. 문서 목록은 `/api/project-documents/<id>/<plans|resources>/items`, 개별 문서는 뒤에 `/<document-id>`를 붙입니다. 추가 문서는 같은 비공개 저장소의 `project-document:<id>:<section>:<document-id>` 키에 따로 저장합니다. GET 요청은 저장소를 이관하거나 변경하지 않습니다.

## GitHub 파일로 추가·수정·삭제

공개 블로그에는 **View·Sign in**을 표시합니다. Sign in에서 사이트 소유자의 GitHub 계정으로 로그인하면 같은 화면의 보호된 편집 주소로 이동합니다. 아래의 Edit·글 관리 기능은 이 편집 주소에서만 제공하며, 화면의 문구를 직접 고치는 방식은 유지합니다. 서버 연결과 검사 범위는 [GitHub 소유자 로그인](AUTHOR-LOGIN.md)에 있습니다.

글 본문에서 상단의 **Edit ↗**를 누르면 해당 Markdown 파일의 GitHub 편집 화면이 새 탭으로 열립니다. 목록에서 글을 다시 찾을 필요 없이 본문과 메타데이터를 수정할 수 있습니다. GitHub 로그인과 저장소 쓰기 권한이 필요하며 **Commit changes**로 저장합니다.

로그인 후 Home·Writing·주제·시리즈·Portfolio 목록·Projects·DCB에서 **Edit**를 누르면 현재 주소에 편집 항목이 열립니다. Home은 고정 글과 순서를, DCB는 해당 화면의 영상·GIF를 그 자리에서 수정합니다. 목록은 현재 주제·시리즈·기능에 속한 공개 글을 선택해 원문을 수정하고, 소개·목록 설정은 표시된 해당 원본 링크에서 수정합니다. **View**는 편집 항목을 닫으며 검색 조건과 문단 위치를 유지합니다. 새 글·삭제·공개 범위 등 전체 관리 기능은 화면 하단의 **전체 관리**에서 엽니다. 공개 https://imjae.github.io/editor/ 는 로그인 안내로 연결되며, 실제 파일 저장은 GitHub의 인증된 편집 기능에서 진행합니다.

포트폴리오(`/portfolio/2027/`)는 상단 **Edit**를 누른 뒤 화면의 문구를 클릭해 직접 수정합니다. 소개·목차 제목·구역 안내·구현 사례 문구를 편집하며, **View**는 현재 편집의 미리보기입니다. 자동 번호·순서·주소는 유지합니다. **변경 취소**는 게시된 값으로 되돌립니다. 문구는 각 1~600자이며 긴 변경은 여러 **변경 저장** 버튼으로 나눕니다.

**변경 저장**을 누르면 필요한 JSON 파일 내용이 자동으로 채워진 GitHub 저장 화면이 열립니다. 파일 문법을 직접 작성할 필요 없이 로그인 후 **Commit changes**로 저장을 확정합니다. 여러 버튼이 있으면 각각 확정해야 전체 변경이 반영됩니다. 배포 완료 전에는 현재 탭의 미리보기에만 적용됩니다. 영상·GIF 주소는 기존 영상 설정에서 관리합니다.

공개 글의 Edit·포트폴리오 문구·홈 고정·영상 설정을 저장할 때는 **저장·배포** 진행창이 원래 화면에 남습니다. GitHub 커밋 창에서 **Commit changes**를 완료한 뒤 창을 닫으면 저장한 커밋과 공개 블로그·편집 화면의 반영 상태를 확인합니다. 창이 제한되면 진행창의 **GitHub 저장 화면 열기**를 사용합니다. 분할 저장은 각 GitHub 저장을 확정해야 합니다.

두 서버에 반영되면 **수정한 위치에서 최신 버전 보기**가 표시됩니다. 이 버튼을 눌러야 최신 화면으로 이동하며 수정하던 글·구역과 스크롤 위치를 복원합니다. 저장 뒤 추가한 편집을 자동으로 지우거나 강제로 새로고침하지 않습니다. 진행 기록도 같은 탭의 새로고침에서 복원하며, 실패·조회 제한은 안내와 **다시 확인**, 각 배포의 **기록**으로 확인합니다. 새 글 초안 작성·삭제·GitHub의 다른 저장소 작업은 기존 저장 흐름을 유지합니다.

미저장 문구는 같은 탭·같은 사이트의 세션에 보관해 새로고침 시 복원합니다. 게시된 내용이 바뀌면 이전 임시 편집을 자동으로 덮어쓰지 않고 **이전 임시 편집 복원**으로 선택하게 합니다. 공용 기기에서는 작업 후 변경 취소를 누릅니다. 사이트는 GitHub 토큰을 받거나 저장하지 않습니다.

공개 저장은 `content/portfolio-copy/`의 변경 문구만 담은 JSON으로 기록합니다. 빌드는 문구별 최신 설정을 적용하고 미수정 문구는 기존 기본값을 사용합니다. 기본 문구는 `src/data/krafton-2027.ts`와 `src/data/portfolio-page-copy.ts`에 있습니다. 원본의 기본 문구보다 저장 설정이 우선하므로, 설정 이후에는 같은 화면의 Edit에서 수정하거나 해당 설정을 Git에서 되돌립니다.

- **새 글:** 제목·요약·주소·분류를 입력하고 **GitHub에서 새 글 작성**을 누릅니다. 기본 정보와 본문 틀이 채워진 화면에서 이어서 작성합니다. 새 글은 `draft: true`로 시작합니다.
- **수정:** 글 본문 상단의 **Edit ↗** 또는 관리 목록에서 해당 글의 **수정**을 누릅니다. 본문과 메타데이터를 편집하고 **Commit changes**로 저장합니다. 기존 `slug`는 유지합니다.
- **삭제:** 해당 글의 **삭제 검토**를 누릅니다. GitHub에서 파일과 변경 내용을 확인하고 삭제를 커밋하면 반영됩니다. 원본 Jekyll 보관 파일은 별도로 유지합니다.
- **초안:** **초안·전체 파일**에서 GitHub의 파일 목록을 엽니다. `draft: true`인 글은 블로그의 수정 모드 목록에도 표시하지 않습니다.
- **홈 고정 글:** 공개 글 목록의 **고정·고정 해제**로 선택하고, 위의 **홈 고정 글**에서 ↑·↓로 순서를 바꿉니다. **GitHub에서 고정 설정 저장**을 누른 뒤 GitHub에서 **Commit changes**로 확정합니다. 배포가 끝나면 Home과 수정 모드에 같은 순서가 반영됩니다. 저장 전 변경은 현재 탭의 세션에 보관하며, **변경 취소**는 현재 게시된 설정으로 되돌립니다.
- **DCB 영상·GIF:** 프로젝트 소개나 기능 페이지의 **Edit → 이 페이지의 영상·GIF 수정**에서 해당 화면에 표시하는 영상만 수정합니다. 모든 영상은 **전체 관리**에서도 수정할 수 있습니다. 입력 중인 주소는 같은 탭의 새로고침에도 유지합니다. YouTube 주소, HTTPS MP4·WebM·GIF 파일 주소 또는 저장소 GIF 경로를 입력하고 해당 항목의 **GitHub에서 저장** → **Commit changes**로 확정합니다. 배포 후 포트폴리오의 해당 영상 칸에 표시됩니다. **변경 취소**는 해당 입력만 게시된 값으로 되돌리고, 주소를 비워 저장하면 해당 영상 칸을 준비 상태로 되돌립니다. 다른 항목의 주소는 유지합니다. 기존 DCB 프로젝트 소개의 **게임 영상 보기**는 전체 플레이 주소로 연결합니다.

공개하려면 `draft: false`로 바꿔 `main`에 저장합니다. 검증과 배포가 끝나면 블로그에 반영됩니다. **배포 확인**에서 성공 여부를 확인할 수 있습니다. 블로그의 본문에는 Markdown을 사용합니다. GitHub의 Preview는 일부 수식·다이어그램 표시가 블로그와 다를 수 있습니다.

공개 `/editor/`에는 로그인 안내만 표시합니다. 관리 화면은 Cloudflare Worker가 허용한 GitHub 고유 ID의 세션에만 제공합니다. 계정 확인용 GitHub 토큰은 서버에서만 잠시 사용하고 저장하거나 브라우저에 보내지 않습니다. GitHub가 실제 파일 저장 권한을 확인합니다. 기능별 동작은 [GitHub 파일 관리 안내](https://docs.github.com/en/repositories/working-with-files/managing-files)를 참고합니다.

DCB 영상 설정은 `content/project-videos/`의 새 JSON 파일로 저장합니다. 기능별 설정은 `slot`으로 구분하며 같은 항목에서 `createdAt`이 가장 최근인 설정의 `videoUrl`을 사용합니다. `slot`이 없는 기존 설정은 전체 플레이 주소로 유지합니다. 빈 문자열은 해당 영상 칸을 비우는 설정이며, 다른 항목의 저장·제거는 영향을 주지 않습니다. 등록 설정은 전용 데이터의 기존 영상보다 우선하며, 제거 후 이전 영상이 다시 나타나지 않습니다. YouTube는 페이지 안의 플레이어, MP4·WebM은 브라우저 재생 컨트롤을 사용하고 사용자가 재생을 시작합니다. GIF는 이미지로 자동 재생하며 원본 링크도 제공합니다. 이 기능은 영상·GIF 주소만 연결하며 파일 업로드·공개 범위를 변경하지 않습니다.

포트폴리오는 전체 플레이 영상 1개와 전투·IK·장비·물·불의 상세 영상 각 1개로 구성하며 모두 수정 모드에서 관리합니다. AI 활용 영역은 영상 없이 활용 사례와 작업 절차를 설명합니다. 등록 화면의 이름과 저장 식별자는 `src/lib/project-video.mjs`의 `projectVideoSlots`에서 관리합니다. 등록 설정이 없으면 `src/data/krafton-2027.ts`의 `project`·`clientCases`·`graphicsCases`에 지정한 `media`를 기본값으로 사용합니다. 기본 미디어에는 `url`·`title`·`caption`을 함께 지정하고, YouTube는 `startSeconds`·`endSeconds`로 구간을 지정할 수 있습니다. 미등록 영상 영역은 재생 버튼이나 가짜 썸네일 대신 ‘영상 준비 중’을 표시합니다.

모든 영상 칸에 GIF를 연결할 수 있습니다. GIF 파일을 `public/assets/`에 추가한 뒤 수정 모드의 해당 입력에 `/assets/demo.gif`처럼 지정하거나, `.gif`로 끝나는 HTTPS 파일 주소를 사용합니다. GIF의 반복 횟수는 파일 설정을 따르므로 ‘무한 반복’으로 내보낸 파일을 사용합니다. GIF에는 YouTube의 시작·종료 구간 설정을 적용하지 않습니다.

## 소개 페이지

포트폴리오 목록(`/portfolio/`)에는 **DCB 프로젝트**(`/portfolio/2027/`)와 **언리얼 엔진 포팅**(`/portfolio/unreal-porting/`)을 표시합니다. 두 항목 모두 독립된 포트폴리오 페이지입니다. 포팅 페이지는 옮긴 기능의 현재 범위, 진행 중인 C++ 작업과 후속 이식·통합 작업을 구분합니다. 주차별 과정(`/series/dcb-unreal-port/`)은 하단의 상세 자료로 연결하며, 공개 글 수를 게임 기능의 완료 수로 대신하지 않습니다. 포팅 페이지는 로그인 후 Edit에서 해당 Astro 파일을 GitHub로 열어 수정하고 Commit changes로 저장합니다. DCB의 전체 기능 소개는 별도 프로젝트(`/projects/dcb/`)로 관리하며, 포트폴리오 본문에서 참조합니다. 예전 `/portfolio/dcb/`와 기능별 주소는 새 프로젝트 주소로 정적 이동합니다.

`/about/`는 짧은 소개, 하는 일, 관심 분야, 연락처와 인물 사진으로 구성합니다. 상단 메뉴의 **About**과 예전 `/profile/` 주소가 여기로 연결됩니다. **Edit는 현재 보고 있는 페이지를 수정하는 것이 기본**입니다. About에서 로그인 후 Edit를 누르면 같은 주소에서 소개와 연락처 입력란을 표시합니다. View는 변경 내용을 같은 화면에서 미리 보여 줍니다.

이름·짧은 소개·하는 일·관심 분야·이메일·GitHub 주소를 수정하고 **변경 저장**을 누르면 GitHub 저장 화면이 열립니다. **Commit changes**로 확정한 뒤 공개·편집 배포가 끝나면 About에 반영됩니다. 수정 값은 `content/about-copy/`에 항목별로 저장하고 기존 저장·배포 진행창이 About으로 복귀시킵니다. 미저장 편집은 같은 탭에서 새로고침해도 유지하며 새 배포와 충돌하면 **이전 임시 편집 복원**을 선택할 수 있습니다. **변경 취소**는 게시된 값으로 돌립니다.

배치는 `src/pages/about.astro`, 기본 프로필은 `src/data/about.ts`의 `profile`에서 관리합니다. GitHub 기본 주소는 `src/data/site.ts`를 사용합니다. 저장한 항목은 기본값보다 우선하고 About 안의 링크에만 적용합니다. 소개의 줄바꿈은 유지하며 이메일을 비우면 `[이메일 입력]`을 표시합니다. 공개 빌드에는 편집 양식·상태·버튼을 포함하지 않습니다.

`portrait`에는 `src/assets/`에서 불러온 사진 `image`와 대체 설명 `alt`를 지정합니다. 현재 사진은 사용자가 제공하고 배포를 승인한 원본이며, `src/assets/about/mountain-portrait.jpg`에 보관합니다. 인물 전신과 뒤편 산이 함께 보이도록 4:5 영역의 아래쪽을 기준으로 표시하고 Astro가 WebP로 최적화합니다. About은 아이보리 배경에 큰 사진을 왼쪽, 소개와 정보를 오른쪽에 배치합니다. 모바일은 사진 다음에 정보를 표시하고, Edit에서는 편집 양식을 사진 위로 올려 바로 입력할 수 있게 합니다. 하는 일의 기본값은 게임 개발자 · Unity, C# · Unreal Engine, C++입니다. About에는 프로젝트 앨범을 두지 않습니다. 확정한 사실만 `~합니다 / ~했습니다`체로 채우고 [문구 지침](EDITORIAL.md)을 따릅니다. 이 파일은 공개 빌드에 포함되므로 공개할 정보만 입력합니다.

## 독서 기록

`/topics/reading/`은 책 제목·저자·완독일과 짧은 감상을 보여주는 Bookshelf입니다. 완독일이 비어 있으면 글 작성일을 **기록** 날짜로 표시합니다. 짧은 감상이 없는 기존 글은 설명을 **기록 요약**으로 표시합니다. 제목이나 **독서 메모 읽기**를 누르면 같은 글의 본문으로 이동합니다.

제목·저자만 있는 책은 `content/reading-list/`의 JSON으로 관리하고 **감상 미작성**으로 표시합니다. 이 항목은 완독한 책이나 독후감으로 취급하지 않습니다. 기록 종류에서 **전체 기록·독서 메모·감상 미작성**을 골라 볼 수 있습니다. **감상 남기기**를 누르면 책 제목·저자·글 주소가 채워진 새 글 양식을 엽니다. 감상을 게시하면 같은 slug의 목록 항목 대신 글을 표시하므로 책이 두 번 나오지 않습니다. 본문 검색과 Writing에는 실제로 작성한 글만 포함하고, Books에서는 감상 없는 책도 제목·저자와 원래 노션 제목으로 찾을 수 있습니다.

노션에서 이관한 책과 원문 날짜·중복 처리 근거는 [독서 이관 기록](READING-MIGRATION.md)과 [날짜 근거 데이터](READING-MIGRATION.json)에 있습니다. 새 독후감을 직접 작성할 때는 기본 작성일을 사용하고, 기존 노션 메모를 옮길 때만 중심 원문의 생성일과 `dateBasis: notion`을 지정합니다. 관람일·목록에 추가한 날·최종 수정일을 독후감 원문 작성일이나 완독일로 대신하지 않습니다.

Books의 **독서 기록 추가** 또는 Edit에서 Topic을 **Books**으로 선택합니다. 글 제목·요약·주소·작성 날짜와 함께 책 제목(필수), 저자·완독일·짧은 감상(선택)을 입력합니다. 글 종류는 `reading`으로 지정되고, 짧은 감상은 최대 280자까지 목록과 글 상단에 표시됩니다. 저장은 기존과 같이 GitHub에서 합니다. 새 기록은 초안이며 `draft: false`로 공개한 뒤 배포해야 목록·검색에 나타납니다. 본문에는 긴 독후감이나 추가 메모를 이어 쓸 수 있습니다.

로컬 생성 예시:

```sh
npm run new -- --title "책 제목 독서 메모" --slug book-reading-note --topic reading --book-title "책 제목" --book-author "저자" --book-note "직접 작성한 짧은 감상"
```

완독일을 알고 있으면 `--book-finished "2026-10-19"`처럼 추가합니다. 메타데이터는 다음 형식이며 선택 항목은 생략할 수 있습니다.

```yaml
topic: reading
kind: reading
book:
  title: "책 제목"
  author: "저자"
  finished: "2026-10-19"
  note: "직접 작성한 짧은 감상"
draft: true
```

새 파일은 `content/articles/reading/`에 둡니다. 기존 「시지프 신화」 글은 이 폴더로 옮겼으며, 원래 날짜·slug·본문과 `legacy/jekyll/` 원본을 유지합니다. 부분 독서 메모이므로 완독일과 새 감상을 임의로 추가하지 않습니다.

## 로컬에서 작성

### 1 새 글 만들기

```sh
npm run new -- --title "손 지지가 끊기는 Climb 전환" --slug climb-hand-contact --topic gameplay --kind devlog --project dcb --series dcb
```

주소는 영문 소문자·숫자·하이픈으로 정하고 공개 후 유지합니다. 같은 주소가 있으면 덮어쓰지 않습니다. `kind`는 `case-study` 구조 노트, `devlog` 개발 기록, `note` 기술 노트, `reading` 읽기 노트입니다.

### 2 메타데이터 채우기

```yaml
---
title: "손 지지가 끊기는 Climb 전환"
description: "같은 지형과 입력에서 접촉 해제 시점을 비교한 기록입니다."
slug: "climb-hand-contact"
date: "2026-10-17"
topic: "gameplay"
kind: "devlog"
tags: ["Unity", "IK", "Traversal"]
project: "dcb"
series: "dcb"
order: 7
draft: true
---
```

날짜는 한국 기준 `YYYY-MM-DD`입니다. 글 생성 명령이 오늘 날짜를 채웁니다. 큰 수정에는 `updated`를 추가합니다. DCB 시리즈 글은 `order` 순으로 연결되고, 태그는 기존 표기를 재사용합니다.

Home은 8개 주제 표지에 공개 글 수와 대표 글의 제목·독서 메모·도식을 표시합니다. 표지를 누르면 아래에 해당 주제의 글이 표시되고, 기본 목록에는 최근 글 5편이 나옵니다. Home 검색은 제목·요약·태그·책 정보를 찾으며, 전체 본문 검색과 서버 공개 글은 Writing에서 제공합니다. 카테고리·태그·검색·고정 보기 상태는 주소와 뒤로 가기에서 복원됩니다. JavaScript를 사용할 수 없으면 표지가 기존 주제 페이지로 이동합니다.

카테고리를 선택하면 글 목록 위에 해당 공개 글들이 사용한 태그와 태그별 글 수를 표시합니다. 태그는 한 번에 하나를 선택하고 검색어와 함께 적용합니다. 태그 옆 숫자는 검색어·태그 선택 전의 카테고리 전체 글 수를 기준으로 하므로 검색 결과가 없어도 다른 태그를 고를 수 있습니다. 같은 태그를 다시 누르거나 **전체**를 누르면 태그만 해제하고, 카테고리 변경·고정 글 전환·필터 초기화는 이전 태그를 해제합니다. **전체 글 보기**는 카테고리·태그·검색어를 Writing으로 전달합니다. 사용한 태그가 없는 카테고리는 태그 영역을 표시하지 않습니다.

기존 고정 글은 목록 옆의 **고정 글** 버튼으로 전환하며 저장된 순서를 따릅니다. 표지 대표 글은 `src/data/home-covers.ts`에서 별도로 선택하고 실제 공개 글에서 제목과 독서 메모를 읽습니다. 미리보기 도식은 `HomeCoverDiagram.astro`에서 글 내용을 작은 정적 SVG로 표현합니다. 글의 slug에 연결하므로 해당 글이 없거나 비공개가 되면 같은 주제의 최신 공개 글과 요약으로 대체하며 이전 도식을 붙이지 않습니다. Books의 고도 글은 기존 독서 메모의 두 번째 문장을 사용합니다. 글 본문의 밝은 배경과 코드 강조색은 유지합니다. 고정 설정과 순서는 Home의 Edit 또는 전체 관리에서 관리합니다. 저장 버튼은 선택한 slug 순서를 담은 `content/pins/<시각>-<식별자>.json` 새 파일 작성 화면을 엽니다. 기존 글 본문을 재작성하지 않고 전체 고정 목록을 한 번의 GitHub 커밋으로 저장하기 위한 방식입니다. 브라우저에서 API 토큰을 받거나 저장하지 않습니다.

빌드는 유효한 설정 중 `createdAt`이 가장 최근인 목록을 사용합니다. 빈 `pins: []`도 전체 해제 설정으로 반영합니다. 삭제되거나 초안인 글은 표시하지 않고 나머지 글의 순서를 유지합니다. 설정을 되돌릴 때는 수정 모드에서 원하는 순서로 다시 저장하거나 해당 변경을 Git에서 되돌립니다. JSON 설정이 아직 없을 때만 글의 기존 `pinned: true`·`pinOrder` 메타데이터를 사용합니다. JSON이 생긴 뒤에는 글 메타데이터만 바꾸어도 고정 설정이 바뀌지 않습니다.

기존 기록을 옮기는 글은 출처 날짜를 사용합니다. 노션 기반 글은 중심 원문의 **생성일**을 `date`에 쓰고 `dateBasis: "notion"`을 지정합니다. 마지막 수정일을 생성일 대신 쓰지 않습니다. 작업 이력 기반 글은 본문에서 다룬 대표 커밋의 작성 시각(AuthorDate)을 한국 날짜로 바꾸고 `dateBasis: "commit"`을 씁니다. 체리픽·병합 후의 반영일(CommitDate)과 구분합니다. 참고 자료가 여러 개면 중심 원문과 보조 자료를 구분합니다.

새로 작성한 학습 글·블로그 목차는 실제 블로그 작성일을 사용합니다(`dateBasis` 기본값은 `authored`). Jekyll 원본 두 글은 기존 작성일과 주소를 유지합니다(`legacy`). 원문 날짜로 바꾸거나 본문을 보완하면 `updated`에 해당 수정일을 기록합니다. 화면에는 노션 원문·작업 기록 날짜와 수정일을 구분해 표시합니다. 2026년 10월 전체 조사 결과와 글별 근거는 [날짜 조사 기록](ARTICLE-DATES.md), [날짜 근거 데이터](ARTICLE-DATES.json)에 있습니다.

### 3 본문 구성

대표 사례는 **문제 → 구조와 구현 → 선택한 이유와 비용 → 결과**로 작성합니다. 검사 통과 건수·자료 대조 보고·남은 확인·글 작성 중 미실행 고지는 공개 본문에 넣지 않고 내부 기록에 남깁니다. 설명과 요약은 `~했습니다 / ~합니다`체로 맞춥니다. 제목은 위 메타데이터가 표시하므로 본문은 `##`부터 시작합니다. `##`, `###`는 우측 목차에 자동으로 나타납니다.

코드 블록에 `csharp`, `hlsl`, `json` 등의 언어를 적으면 강조와 복사 버튼이 붙습니다. 흐름도는 `mermaid` 코드 블록으로, 수식은 `$...$` 또는 `$$...$$`로 작성합니다. 표는 일반 Markdown 표를 사용합니다.

이미지는 `public/media/글주소/`에 넣고 `/media/글주소/이미지.webp`처럼 참조합니다. 큰 영상은 사용자 소유의 공개 영상 링크를 사용합니다. 실제 장면이 준비되지 않았으면 영상 버튼이나 가짜 썸네일을 만들지 않습니다.

실제 플레이 영상은 [촬영·첨부 계획](DCB-CAPTURE-PLAN.md)을 따릅니다. 사용자 선택에 따라 YouTube 등에 업로드한 뒤 본문에 삽입합니다. 원본은 Git에서 제외한 `media-inbox/`에 보관하고, 별도로 쓸 실제 대표 이미지만 `public/media/<slug>/`에 넣습니다. [촬영 기록](templates/DCB-TAKE.md)에 커밋·실행 환경·타임코드·확인 범위를 남기고 [YouTube 양식](templates/youtube-figure.html)을 실제 영상 ID와 설명으로 채웁니다. `.article-video`는 16:9 비율과 최소 높이 200px로 영상·캡션을 표시하며, 자동 재생 없이 지연 로드·모바일 인라인 재생·전체 화면과 원본 링크를 제공합니다. 실제 YouTube 영상이 준비되기 전에는 양식을 공개 글에 붙이지 않습니다.

### 4 로컬에서 보기

`npm run dev`의 주소를 엽니다. 이때 초안에는 로컬 표시가 붙습니다. 공개 상태를 확인하려면 `npm run verify` 후 `npm run preview`를 사용합니다. 초안은 정적 페이지·목록·본문 검색·RSS·sitemap에 포함되지 않습니다.

제목과 본문, 태그는 글 모아보기에서 함께 검색합니다. 검색어와 필터는 URL에 반영되어 같은 결과를 링크로 공유할 수 있습니다. 검색창 단축키는 `/`입니다.

### 5 공개하기

설명과 본문을 완성한 뒤 `draft: false`로 바꿉니다. `npm run verify`를 통과하고 커밋한 뒤 `main`에 push합니다. Actions의 배포가 성공하면 같은 주소에 반영됩니다.

DCB 소개의 **구현한 기능**은 `src/data/dcb-features.mjs`에서 관리합니다. 기능의 `title`·`description`은 글 제목과 별도입니다. `overviewSlug`에 현재 기능 설명 한 편을 지정하고, `articleSlugs`에는 그 아래에 표시할 구현·분석 글을 읽는 순서대로 넣습니다. 기능을 누르면 `/projects/dcb/features/<기능 slug>/`에서 **기능 설명 → 구현·분석 글** 두 영역으로 보여 줍니다. 중복 지정한 설명 글은 분석 목록에 다시 표시하지 않습니다. 공개 빌드는 초안·삭제된 글을 제외하고 로컬 dev에서만 초안 배지를 붙여 표시합니다. 기능의 전체 글 수와 sitemap도 같은 설정을 사용합니다. 설명이 없거나 초안이어도 분석 목록과 기능 제목은 유지하며 기존 글 주소는 바꾸지 않습니다. 기능별 순서는 시리즈의 `order`와 별개입니다.

현재 여러 경로의 동작을 종합해 새로 작성한 기능 안내는 블로그 작성일과 `dateBasis: authored`를 사용합니다. 기존 작업 분석을 분리한 글은 설명하는 원래 작업의 대표 커밋 날짜를 유지합니다. 첫 글은 현재 사용 흐름·화면·규칙을 먼저 설명하고, 구체적인 수정과 성능 비교는 분석 글로 연결합니다.

이동 속도·스태미너·회복·행동/입력 제어의 분석은 기능 `gameplay-balancing`과 태그 `Balancing`으로 묶습니다. 분류는 기존 `gameplay`, 시리즈는 `dcb`를 유지합니다. [밸런싱 글 구성](DCB-BALANCING-PLAN.md)의 순서와 [작성 양식](templates/DCB-BALANCE-CASE.md)을 참고해 초안으로 시작하고, 공개된 분석을 해당 기능의 `articleSlugs`에 추가합니다. 짐·다리의 물리 표현과 이동 규칙의 관련 링크는 유지하되 기능별 분석 목록에서 구분합니다.

밸런스 값을 편집·관찰하는 에디터 도구 제작 경험은 `tools`에 두고, 같은 `Balancing` 태그와 DCB 기능 목록으로 연결합니다. 계산 표와 런타임 계측 등 도구가 제공하는 기능을 설명합니다.

공개 전에는 원본 자산과 본인 기여, AI 보조 범위, 실제 측정 조건을 확인합니다. private 게임 저장소의 전체 코드·로컬 경로·로그·세이브는 블로그에 복사하지 않습니다.
