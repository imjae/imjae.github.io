## 이번 구간에서 찾을 연결

첫 주에는 DCB 전환본에서 플레이어가 생성되고, 입력을 받아 움직이며, HUD를 표시하고, 귀환 결과를 저장하는 경로를 찾습니다. 이후 기능을 바꿀 때 어느 객체와 에셋을 수정할지 설명할 수 있는 상태를 만듭니다.

아래 순서는 Unreal Engine 5.8 전환본을 기준으로 한 실행·관찰 과제입니다. 이 글의 절차에 따라 직접 확인한 결과를 적고, 예상과 다른 동작은 다음 수정 항목으로 남깁니다. 전체 순서는 [12주 계획](/writing/dcb-unreal-port-study-plan/), 다른 글은 [과정 목록](/series/dcb-unreal-port/)에서 봅니다.

## 1일차: 열리는 장면과 조작할 장면을 구분합니다

현재 기본 시작 맵은 `L_GameScene_01`입니다. 기존 장면을 옮긴 맵이므로 프로젝트를 열었다는 사실만으로 플레이어와 전체 게임 흐름이 연결되었다고 판단하지 않습니다. Content Browser에서 다음 이름을 검색해 역할을 구분합니다.

| 맵 | 역할 | 첫 주에 할 일 |
| --- | --- | --- |
| `L_GameScene_01` | 기존 장면의 변환 결과 | 지형·배치·재질이 있는 위치를 살펴봅니다. |
| `L_RuntimePort_Validation` | 이동·채집·전투·귀환을 확인하는 작은 구간 | 처음 조작하고 호출 경로를 찾을 기준으로 사용합니다. |
| `L_GameScene_01_Playable` | 기존 장면을 불러오고 플레이 요소를 더한 맵 | 작은 구간과 실제 장면의 차이를 이후 비교합니다. |

먼저 `L_RuntimePort_Validation`을 열고 World Settings의 GameMode Override를 확인합니다. 지정되어 있으면 해당 GameMode를, 비어 있으면 Project Settings의 Maps & Modes에서 기본 GameMode를 확인합니다. Default Pawn Class와 Player Controller Class를 따라가 실제 생성할 클래스를 찾습니다.

이어서 Play의 Selected Viewport로 실행합니다. 아래 입력을 하나씩 시도하고 성공 여부와 화면 변화를 적습니다. 키를 누를 때 게임 뷰가 입력 포커스를 갖고 있는지도 확인합니다.

| 입력 | 현재 연결된 행동 | 관찰할 내용 |
| --- | --- | --- |
| WASD·마우스 | 이동·시점 | 캐릭터 방향과 카메라 회전이 어떻게 나뉘는지 봅니다. |
| Shift·Ctrl | 질주·걷기 전환 | 속도와 스태미너 표시를 함께 봅니다. |
| G·F | 지게 상태 전환·상호작용 | 채집 전후의 적재량과 안내 문구를 봅니다. |
| 마우스 왼쪽·Space | 기본 공격·회피 | 모션 시작과 실제 이동·피해 시점을 구분합니다. |
| I·Esc | 인벤토리 열기·닫기 | 커서, 포커스, 이동 입력과 선택·내려놓기를 봅니다. |
| 사망 뒤 R | 재출발 | 체력·스태미너·적재 상태가 어떻게 바뀌는지 봅니다. |

현재 작은 구간의 귀환은 캠프 위치로 돌아오는 방식입니다. 로비와 필드를 전환하는 기능은 8주차에 연결합니다. 첫 실행 결과를 적은 뒤에만 별도 이름의 실험용 맵을 만들고, 원본 검증 맵을 비교 기준으로 유지합니다. 복제한 맵이 같은 캐릭터·DataAsset을 참조하면 그 에셋의 수정은 원본에도 영향을 주므로, 바꿀 에셋도 파생본으로 분리합니다.

## 2일차: 생성·조종·표시의 담당 객체를 찾습니다

Unity에서 한 플레이어 컴포넌트에 모여 있던 책임을 언리얼에서는 여러 객체가 나누어 가질 수 있습니다. 이름을 일대일로 바꾸기보다 현재 전환본의 연결을 확인합니다. GameMode·Controller·Pawn·Character의 기본 역할은 Epic의 [Gameplay Framework](https://dev.epicgames.com/documentation/unreal-engine/gameplay-framework-in-unreal-engine?lang=en-US)를 함께 봅니다.

| 담당 객체 | 이 구간에서 찾을 책임 | 직접 확인할 위치 |
| --- | --- | --- |
| GameMode | 플레이어와 Controller의 기본 클래스 | World Settings, GameMode 기본값 |
| PlayerController | 조종할 Pawn, HUD 생성, 인벤토리 입력 모드 | Possession, BeginPlay, 위젯 생성 경로 |
| Character | 충돌 캡슐, 메시, 카메라, 이동 요청 | Components, CharacterMovement, 입력 바인딩 |
| 플레이어 상태 컴포넌트 | 체력·스태미너·적재 상태 | Character의 컴포넌트와 상태 갱신 경로 |
| GameInstanceSubsystem | 출정 결과와 저장 객체의 접근 | 저장 불러오기·귀환 처리 경로 |
| SaveGame | 디스크에 남길 값 | 아이템 ID·수량·귀환 결과의 저장 필드 |

전환본의 플레이어 상태 컴포넌트는 이름에 PlayerState가 있어도 엔진의 `APlayerState`와 같은 타입이라고 가정하지 않습니다. 실제 상속과 소유자를 확인합니다.

PIE를 실행한 상태에서 World Outliner의 플레이어를 선택하고, 조종 중인 Pawn과 Controller가 예상한 클래스인지 봅니다. 블루프린트 디버그 대상을 실제 인스턴스로 선택하거나 C++ 중단점을 이용해 생성·BeginPlay·입력 설정 경로를 따라갑니다. 관찰한 호출 순서를 적되, 서로 다른 Actor의 BeginPlay 순서를 고정된 약속으로 만들지 않습니다.

이날의 결과물은 **GameMode → Controller/Pawn 생성과 조종 → Character 입력·이동**, **Controller → HUD**, **플레이어 상태 → 출정 결과 → 저장 객체**의 관계도입니다. 하나의 순차 실행 그림으로 합치기보다 생성 관계와 데이터 전달 관계를 구분해서 그립니다.

## 3일차: 입력 하나가 이동으로 이어지는 경로를 봅니다

W 입력 하나를 고릅니다. Mapping Context에서 어떤 Input Action에 연결되는지 확인하고, 캐릭터의 입력 바인딩에서 이동 값이 저장되는 위치를 찾습니다. 이어서 `AddMovementInput`과 CharacterMovement의 속도 적용까지 따라갑니다. [Enhanced Input](https://dev.epicgames.com/documentation/en-us/unreal-engine/enhanced-input-in-unreal-engine)

처음에는 속도·가속·감속·짐 무게를 동시에 바꾸지 않습니다. 같은 출발점에서 같은 시간 동안 이동한 뒤 정지하는 동작을 기준으로 정합니다. 실험용 밸런스 DataAsset의 값 하나만 바꾸고, 실행 중 적용된 값과 위치 변화를 비교한 뒤 복원합니다.

| 변형 | 먼저 예상할 일 | 실행 후 적을 일 |
| --- | --- | --- |
| 이동 입력을 놓습니다. | 이동 요청과 감속이 어떻게 끝나는지 예상합니다. | 입력 값·속도·정지 위치를 적습니다. |
| 지게를 든 상태에서 같은 입력을 줍니다. | 부담이 어느 계산에 들어갈지 예상합니다. | 최종 속도를 결정한 값과 함수를 적습니다. |
| 질주 중 인벤토리를 엽니다. | UI와 게임 입력의 담당 객체를 예상합니다. | 이동·시점·질주 상태와 닫은 뒤 동작을 적습니다. |

입력 값은 바뀌는데 캐릭터가 움직이지 않는다면 Possession, 이동 입력 무시 상태, 행동 제한, CharacterMovement와 충돌을 순서대로 확인합니다. 화면의 모션만 보고 이동 처리가 성공했다고 판단하지 않습니다.

## 4일차: HUD와 저장 데이터의 수명을 나눕니다

채집으로 적재량을 바꾼 뒤 HUD와 인벤토리가 어떤 값을 읽는지 찾습니다. 위젯이 게임 상태를 직접 보관하는지, 상태 컴포넌트를 읽어 표시하는지 확인합니다. 인벤토리를 닫았다 열었을 때 데이터가 유지되는 이유도 설명합니다.

그다음 귀환 성공과 사망 뒤 재출발을 각각 수행할 순서를 만듭니다. 성공 시 보관함으로 들어갈 값, 실패 시 잃을 값, 새 출정에서 초기화할 값을 미리 표로 적습니다. 이 과제에서는 기존 개인 저장과 구분되는 실험용 슬롯을 사용합니다. 슬롯 변경과 원상 복구 방법도 함께 적습니다.

GameInstanceSubsystem에 객체가 남아 있는 것과 SaveGame이 디스크에 기록된 것은 다릅니다. PIE 종료 뒤 새 실행과 앱 재시작에서 각각 무엇이 복원되는지 비교합니다. 저장 형식과 호출 방법은 [Saving and Loading Your Game](https://dev.epicgames.com/documentation/unreal-engine/saving-and-loading-your-game-in-unreal-engine?lang=en-US)을 참고합니다.

객체 수명이 헷갈리면 [UObject와 리플렉션](/writing/unreal-uobject-reflection/)과 [객체 수명과 GC](/writing/unreal-object-lifetime-gc/)에서 기본값·인스턴스·참조 해제 부분을 다시 봅니다.

## 5일차: 같은 구간을 반복하고 다음 변경을 하나 고릅니다

**이동 → 채집 → 적재량 확인 → 아이템 내려놓기 → 재수거 → 기본 전투 → 귀환 → 새 실행** 순서를 고정합니다. 앞서 관찰한 행동이 매번 같은 조건에서 재현되는지 확인합니다. 실패한 경우 입력 순서·현재 상태·예상과 실제를 짧게 적습니다.

첫 주에는 다음 네 가지를 설명할 수 있으면 다음 단계로 넘어갑니다.

- 프로젝트를 열 때의 맵과 현재 조작할 맵이 다른 이유를 설명합니다.
- 플레이어 생성·조종·HUD·저장의 담당 객체를 찾아 보여 줍니다.
- 입력 하나와 밸런스 값 하나가 실제 이동에 도달하는 경로를 설명합니다.
- 인벤토리 닫기·귀환·새 실행에서 유지할 값과 초기화할 값을 구분합니다.

다음 변경은 가장 먼저 재현한 문제 하나로 정합니다. 예를 들어 질주 중 UI를 열고 닫았을 때 입력 상태가 어긋난다면 2주차 입력 전환의 첫 과제로 삼습니다. 문제가 없다면 같은 조건에서 짐 무게에 따른 이동을 비교합니다.
